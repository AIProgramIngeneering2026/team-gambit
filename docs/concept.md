# TradeLab — бэктестер торговых стратегий

## 1. Идея в одном предложении

**TradeLab проверяет торговую стратегию на исторических рыночных данных и по результатам проверки формирует сигнал стратегии: `BUY`, `HOLD` или `SELL`. Сигнал отражает результат применения конкретной стратегии к последним доступным рыночным данным и не является индивидуальной инвестиционной рекомендацией.**

Это рабочий инструмент для частного инвестора, который хочет принимать решения на основе проверенных правил, а не интуиции. Основная ценность — быстро перейти от идеи «а что, если покупать по пересечению скользящих средних» к измеримому результату: доходность, просадка, список сделок и текущий сигнал стратегии.

Сервис не совершает сделок и не подключается к брокеру: он исследует стратегии и показывает их сигналы.

## 2. Практическая проблема

Частный инвестор, который хочет торговать по правилам, сталкивается с выбором:

- торговать «на глаз», без проверки идеи на истории;
- писать собственный код для бэктеста, что требует навыков программирования и аккуратной работы с данными;
- использовать профессиональные терминалы — дорогие и избыточные для простых стратегий;
- доверять готовым «сигналам» из интернета без возможности проверить, как они работали в прошлом.

Типичные ошибки при ручной проверке стратегий: подглядывание в будущее (сигнал по данным, которых ещё не было на момент решения), игнорирование комиссий, выбор удачного периода постфактум, отсутствие воспроизводимости результата.

TradeLab должен давать честный и воспроизводимый ответ на вопросы:

- как стратегия с заданными параметрами вела себя на выбранном периоде;
- какие сделки она совершила и с каким результатом;
- каковы доходность, просадка и другие метрики риска;
- какой сигнал стратегия даёт сейчас: покупать, держать или продавать;
- какая из нескольких стратегий показала себя лучше на одном инструменте.

## 3. Целевая аудитория

Основные пользователи:

- активные частные инвесторы, желающие торговать по формальным правилам;
- начинающие алготрейдеры, проверяющие свои первые стратегии;
- аналитики и студенты, изучающие поведение стратегий на реальных данных.

Сервис не рассчитан на высокочастотную торговлю и профессиональных маркет-мейкеров. Его ниша — дневные интервалы, простые интерпретируемые стратегии и понятные результаты.

## 4. Границы MVP

- один рынок: акции Московской биржи;
- 20–30 ликвидных инструментов;
- дневные свечи (OHLCV), без тиковых и минутных данных;
- 3–5 встроенных стратегий с настраиваемыми параметрами;
- один пользователь или небольшая команда без сложной системы ролей;
- учёт комиссии фиксированным процентом от сделки.

Архитектура не должна жёстко зависеть от конкретного рынка и поставщика данных: смена площадки реализуется через новый адаптер рыночных данных.

## 5. Основной пользовательский сценарий

1. Пользователь выбирает инструмент (тикер), стратегию из каталога и задаёт её параметры.
2. Пользователь задаёт период исторических данных и размер комиссии.
3. Сервис создаёт задание на бэктест (Job) и ставит его в очередь.
4. Исполнитель загружает исторические данные у внешнего поставщика, прогоняет стратегию по закрытым барам и фиксирует сделки.
5. Пользователь отслеживает состояние задания и по завершении получает результат: метрики, кривую капитала и список сделок.
6. Пользователь запрашивает текущий сигнал стратегии: сервис применяет выбранную стратегию к последним доступным данным и возвращает значение `BUY`, `HOLD` или `SELL` с обоснованием формирования сигнала.
7. Пользователь запускает другую стратегию на том же инструменте и сравнивает результаты.
8. Пользователь возвращается к истории запусков и повторяет бэктест с теми же параметрами для проверки воспроизводимости.

## 6. Пример результата бэктеста

Все названия и цифры ниже условны.

> ### Стратегия «Пересечение SMA(20/50)» на инструменте `EXMPL`
>
> **Период:** 01.01.2022 — 01.01.2025, дневные свечи, комиссия 0,05%.
>
> **Результат:** доходность +34,2% против +21,5% у «купить и держать», максимальная просадка −12,8%, коэффициент Шарпа 0,9, всего 17 сделок, прибыльных 59%.
>
> **Последняя сделка:** покупка 14.10.2025 по 312,40 по сигналу пересечения SMA20 снизу вверх через SMA50.
>
> **Текущий сигнал стратегии: ** HOLD. Позиция открыта 14.10.2025, условий выхода на последнем закрытом баре (07.11.2025) нет.
>
> **Данные по состоянию на:** 07.11.2025, конец торгового дня.

Сигнал стратегии формируется на основе последних доступных рыночных данных и отражает результат работы алгоритма. Он не является индивидуальной инвестиционной рекомендацией или советом к совершению сделки.

## 7. Функциональные требования MVP

### 7.1. Каталог стратегий

- Каждая стратегия — исполнитель за единым контрактом: на входе ряды свечей и параметры, на выходе список сигналов и сделок.
- Встроенные стратегии MVP:
  - пересечение скользящих средних (SMA crossover);
  - возврат к среднему по RSI;
  - пробой диапазона (breakout);
  - «купить и держать» как базовая линия для сравнения.
- Новая стратегия добавляется регистрацией нового исполнителя без изменения управляющей логики.
- У каждой стратегии — схема параметров с валидацией (диапазоны, типы, значения по умолчанию).

### 7.2. Запуск бэктеста

- Создание задания через API с ключом идемпотентности: повторный запрос с тем же ключом возвращает существующее задание и не создаёт дубликат.
- Валидация параметров до постановки в очередь: неизвестная стратегия, неизвестный тикер, некорректный период — отказ с понятной ошибкой.
- Асинхронное выполнение: задание проходит жизненный цикл состояний, недопустимые переходы отклоняются.
- Отмена задания пользователем до его завершения.
- Повторный запуск с теми же параметрами и тем же снимком данных даёт тот же результат.

### 7.3. Рыночные данные

- Внешний поставщик данных подключается через адаптер `MarketDataProvider` с timeout, ограниченным числом повторов и разбором некорректного ответа.
- Для MVP — публичный API Московской биржи (ISS) или эквивалентный разрешённый источник.
- Полученные свечи кешируются вместе со временем получения; результат бэктеста привязан к конкретному снимку данных для воспроизводимости.
- Недоступность поставщика изолирована: задание завершается с ошибкой, остальные задания продолжают работу.
- Сервис не выдаёт задержанные данные за поток реального времени: у каждого сигнала стратегии указано время последнего использованного бара.

### 7.4. Метрики и результаты

Для каждого завершённого бэктеста сохраняются:

- суммарная доходность и доходность базовой линии «купить и держать»;
- максимальная просадка;
- коэффициент Шарпа;
- число сделок, доля прибыльных, средний результат сделки;
- кривая капитала по времени;
- список сделок с датами, ценами, объёмом и сработавшим правилом.

Сигналы вычисляются только по закрытым барам: решение на баре `t` принимается по данным не позднее закрытия бара `t`, исполнение — не раньше открытия бара `t+1`. Это правило защищает от подглядывания в будущее.

### 7.5. Сигнал стратегии

- Сигнал стратегии формируется применением выбранной стратегии к последним доступным данным инструмента.
- Возможные значения сигнала стратегии: `BUY`, `HOLD`, `SELL` и `INSUFFICIENT_DATA`. Значения `BUY`, `HOLD` и `SELL` обозначают результат работы стратегии, а `INSUFFICIENT_DATA` указывает на невозможность формирования сигнала из-за недостатка данных.
- Сигнал содержит обоснование: какое правило стратегии сработало и какие значения индикаторов были на последнем баре.
- Указывается время последнего использованного бара и время формирования сигнала.
- Если данных недостаточно для расчёта индикаторов (например, история короче необходимого периода), возвращается отдельное значение сигнала `INSUFFICIENT_DATA` с явным пояснением причины. Это значение означает, что стратегия не может сформировать торговый сигнал из-за недостатка данных.

### 7.6. Сравнение стратегий

- Запуск нескольких стратегий на одном инструменте и периоде.
- Сводная таблица метрик по каждому запуску.
- Все сравниваемые запуски используют один и тот же снимок данных.

### 7.7. История запусков

- Список заданий с фильтрами по инструменту, стратегии, состоянию и периоду.
- Карточка завершённого запуска с полным результатом и параметрами.
- Повторный запуск из карточки одной операцией.

## 8. Жизненный цикл Job

Задание на бэктест (`BacktestJob`) проходит состояния:

- `created` — параметры провалидированы, задание сохранено;
- `queued` — задание поставлено в очередь;
- `running` — исполнитель взял задание в работу;
- `completed` — результат рассчитан и сохранён;
- `failed` — выполнение завершилось ошибкой (с кодом и описанием);
- `canceled` — задание отменено пользователем.

Разрешённые переходы:

- `created → queued`, `created → canceled`;
- `queued → running`, `queued → canceled`, `queued → failed`;
- `running → completed`, `running → failed`, `running → canceled`.

Состояния `completed`, `failed`, `canceled` — терминальные, переходов из них нет. Попытка недопустимого перехода отклоняется. Повторный запуск упавшего задания — это новое задание, а не изменение состояния старого.

## 9. Предлагаемая архитектура

```text
            HTTP API (FastAPI, OpenAPI)
                      │
                      ▼
        Создание/валидация BacktestJob
                      │
                      ▼
        Dispatcher ── Registry ── StrategyTool (SMA, RSI, breakout, buy&hold)
                      │
                      ▼
           MarketDataProvider (адаптер)
                      │
                Внешний API рыночных данных
                      │
                      ▼
        PostgreSQL: задания, результаты, снимки данных
```

Технологический вариант реализации:

- **Backend:** Python и FastAPI.
- **База данных:** PostgreSQL (на прототипе — SQLite с теми же миграциями).
- **Асинхронная обработка:** отдельный worker-процесс и очередь.
- **Контракт API:** OpenAPI, единый формат ошибок, идемпотентное создание заданий.
- **Внешняя зависимость:** адаптер `MarketDataProvider` с fake-реализацией для тестов.
- **Наблюдаемость:** структурированные логи с correlation ID, health check, конфигурация из окружения.

## 10. Основные сущности данных

- `Strategy` — тип стратегии, схема параметров, описание.
- `BacktestJob` — задание: параметры, состояние, ключ идемпотентности, временные метки.
- `JobStatusHistory` — история переходов состояний задания.
- `BacktestResult` — метрики и кривая капитала завершённого задания.
- `Trade` — сделка внутри бэктеста: дата, сторона, цена, сработавшее правило.
- `MarketDataSnapshot` — снимок использованных свечей и время их получения.
- `StrategySignal` — сигнал стратегии: значение (`BUY`, `HOLD`, `SELL`), обоснование формирования и время последнего использованного бара.

## 11. Нефункциональные требования

### Корректность

- Сигналы вычисляются только по закрытым барам; подглядывание в будущее исключено на уровне движка.
- Повторный запуск с теми же параметрами и снимком данных даёт идентичный результат.
- Все расчёты метрик сверяются с эталонной реализацией на контрольном наборе данных.

### Надёжность

- Повторный запуск любого этапа не создаёт дубликатов заданий и результатов.
- Сбой поставщика данных изолирован от остального контура.
- После перезапуска worker не теряет задания в очереди и не берёт чужие.
- Бэктест типового периода (3 года дневных свечей) выполняется за секунды; задержка измеряется и логируется.

### Безопасность

- Ключи и токены хранятся только в переменных окружения или менеджере секретов.
- Конфигурация — через окружение, секретов в репозитории нет.
- В логи не попадают секреты.

## 12. Что не входит в MVP

- Реальная торговля и подключение к брокеру.
- Внутридневные и тиковые данные, высокочастотная торговля.
- Стратегии на основе машинного обучения.
- Автоматическая оптимизация параметров и подгонка под историю.
- Портфельный учёт, несколько инструментов в одной стратегии, расчёт налогов.
- Гарантии доходности и индивидуальные инвестиционные рекомендации.
- Богатый пользовательский интерфейс: MVP достаточно API и минимального клиента.

## 13. Проверка качества

### Эталонный набор данных

До оптимизации стратегий команда собирает контрольный набор:

- свечи нескольких инструментов за известные периоды (тренд, боковик, падение);
- заранее рассчитанные вручную или эталонным скриптом результаты для каждой встроенной стратегии;
- периоды с пропусками торговых дней и некорректными данными;
- граничные случаи: история короче окна индикатора, период без сделок.

### Метрики качества

- Расхождение метрик с эталонным расчётом — 0 на контрольном наборе.
- Отсутствие сделок, исполненных до закрытия сигнального бара, — 100% проверок.
- Воспроизводимость: повторный запуск на том же снимке данных даёт идентичные метрики.
- Доля заданий, завершившихся ошибкой без диагностируемой причины, — 0.

## 14. Сквозные критерии готовности MVP

MVP считается завершённым, если выполняются следующие сценарии:

1. Пользователь создаёт задание на бэктест через API без прямого доступа к базе данных.
2. Задание проходит полный жизненный цикл до `completed`, результат содержит метрики и список сделок.
3. Текущий сигнал стратегии содержит значение `BUY`, `HOLD`, `SELL` или `INSUFFICIENT_DATA`, обоснование формирования и время последнего использованного бара. При недостатке данных система возвращает `INSUFFICIENT_DATA` вместо `HOLD`.
4. Повторный запрос создания с тем же ключом идемпотентности возвращает то же задание.
5. Повторный запуск на том же снимке данных даёт идентичные метрики.
6. Невалидные параметры отклоняются до постановки задания в очередь.
7. Недоступность поставщика данных переводит задание в `failed` с диагностикой и не влияет на другие задания.
8. Недопустимый переход состояния (например, отмена завершённого задания) отклоняется.
9. Исторический снимок данных можно повторно проиграть через весь pipeline для воспроизводимой проверки.

## 15. Шов для LLM

Во втором семестре в систему встраивается LLM:

- построение конфигурации стратегии по описанию на естественном языке («покупай, когда RSI ниже 30, продавай выше 70») с валидацией по JSON Schema;
- объяснение результатов бэктеста простым языком с обязательными ссылками на конкретные сделки и метрики;
- подбор стратегий из каталога под сформулированную пользователем идею.

LLM не выдумывает значения индикаторов и не изменяет рассчитанные метрики: она работает только поверх проверяемых результатов движка.

## 16. Распределение работы в команде

Возможное разделение без жёстких границ:

- **Данные и интеграции:** адаптер `MarketDataProvider`, кеширование снимков, fake-сервис, мониторинг внешней зависимости.
- **Backend и API:** жизненный цикл задания, Dispatcher и Registry, HTTP API, хранилище и миграции, идемпотентность.
- **Стратегии и метрики:** исполнители стратегий, расчёт метрик, эталонный набор и сверка корректности.

Схему данных, словарь состояний и критерии приёмки команда согласует до параллельной разработки. Сквозные сценарии принадлежат всей команде.

## 17. Порядок реализации

1. Зафиксировать рынок, инструменты, поставщика данных и правовые ограничения.
2. Согласовать модель задания, состояния и формат результатов.
3. Реализовать адаптер рыночных данных и кеширование снимков.
4. Сделать движок бэктеста с базовой линией «купить и держать» и собрать эталонный набор.
5. Добавить Dispatcher, Registry и встроенные стратегии.
6. Реализовать API: создание заданий с идемпотентностью, статусы, результаты и получение текущего сигнала стратегии.
7. Добавить сравнение стратегий и историю запусков.
8. Провести сверку с эталоном, проверку воспроизводимости и сквозную приёмку.

## 18. Итоговая продуктовая формулировка

**TradeLab помогает инвестору не гадать, а проверять: как стратегия вела себя на истории и какой сигнал — покупать, держать или продавать — она даёт сейчас.**

Главный результат MVP — честный, воспроизводимый бэктест простых стратегий с понятной рекомендацией и защитой от типичных ошибок ручной проверки.
