# Контракт StrategyTool

Контракт определяет вход, результат, ошибки и правила выполнения стратегий TradeLab. Сценарии — в [requirements.md](requirements.md), назначение и границы сервиса — в [concept.md](concept.md). Один интерфейс используется для бэктеста, базовой линии и текущего сигнала.

## 1. Границы ответственности

| Компонент | Ответственность | Что скрывает |
|---|---|---|
| StrategyTool | Проверяет параметры своей стратегии, рассчитывает индикаторы и сигнал последнего закрытого бара | Формулы и торговые правила |
| Registry | Выдаёт Tool по имени и версии, формирует каталог из описаний Tool | Набор зарегистрированных реализаций |
| Dispatcher | Вызывает Tool через общий интерфейс, преобразует неожиданное исключение в `tool_failed` | Выбор конкретной реализации |
| BacktestEngine | Проигрывает историю, исполняет сигналы, ведёт деньги и позицию, формирует сделки, капитал и метрики | Модель исполнения и арифметику расчётов |
| MarketDataService | Выдаёт проверенный неизменяемый снимок свечей и метаданных инструмента | Поставщика, кеш и проверку качества данных |
| JobRunner и JobLifecycle | Организуют выполнение задания и разрешённые переходы состояния | Аренду worker, транзакции и защиту от поздних ответов |
| SignalService | Выбирает окно, запускает проигрывание и собирает ответ текущего сигнала | Сценарий получения сигнала без создания Job |

Tool возвращает решение, а не готовую сделку. Список сигналов и сделок из концепции — результат совместной работы стратегии и общего движка. Tool не меняет Job, позицию, деньги и снимок, не обращается к сети или БД и не выполняет операции брокера.

## 2. Общий интерфейс

```text
name                                      — имя стратегии
version                                   — версия правил и значений по умолчанию
params_schema() → JSON Schema параметров   — типы, диапазоны и значения по умолчанию для каталога
validate_params(params) → normalized_params или ToolError
required_bars(normalized_params) → минимальное число баров
execute(closed_bars, position, normalized_params) → ToolResult или ToolError
```

`normalized_params` — неизменяемые проверенные параметры с подставленными значениями по умолчанию. Они относятся к выбранной паре `(name, version)`: нельзя проверять параметры одной версией, а исполнять другой. `position` — фактическое состояние движка перед решением на текущем закрытии: `flat` или `long`.

`params_schema()` возвращает схему соответствующей версии. `validate_params` применяет те же типы и ограничения и дополнительно проверяет связи полей, например `fast < slow`. Значения `default` в схеме описывают подстановку, которую выполняет `validate_params`, а не заменяют её. Registry не хранит вторую независимую копию схемы.

### Порядок вызовов

1. Входной сценарий ядра проверяет общие поля, получает стратегию из Registry и вызывает `validate_params` до создания Job. Зависимые от стратегии ограничения, включая минимум окна, проверяются после `required_bars`. Неизвестная стратегия и неверные параметры не создают задание.
2. Нормализованные параметры и выбранная версия сохраняются в Job. При выполнении JobRunner проверяет доступность именно этой версии; отсутствие даёт `strategy_unavailable`, а не переход на другую реализацию.
3. MarketDataService получает и проверяет снимок. BacktestEngine последовательно проигрывает бары и через Dispatcher вызывает `execute` с текущей позицией и только доступной к этому моменту историей.
4. Движок проверяет ответ и исполняет торговый сигнал на следующем баре по разделу 8. Tool не решает, когда сохранять результат и менять состояние Job.

Проверка параметров обязательна при прямом обращении к ядру, включая будущий CLI. Проверка только в HTTP-обработчике контракт не выполняет. Повторные вызовы `execute` на одинаковых входах дают одинаковый результат; скрытое изменяемое состояние между вызовами не используется.

## 3. Входные данные

### Свечи и позиция

`closed_bars` — неизменяемая последовательность закрытых дневных свечей в хронологическом порядке. Последний элемент — бар, для которого нужен сигнал. На шаге `t` будущие свечи, в том числе открытие следующего бара, Tool недоступны.

| Поле свечи | Содержание |
|---|---|
| `trading_date` | Торговая дата по календарю инструмента |
| `open_time`, `close_time` | Время открытия и закрытия в UTC, RFC 3339; `open_time < close_time` |
| `open`, `high`, `low`, `close` | Положительные конечные цены; в снимке — десятичные строки, в расчёте — `Decimal` |
| `volume` | Неотрицательный конечный объём |

Обязательно `low <= open <= high` и `low <= close <= high`. Дубли, неверный порядок времени, незакрытые бары, неположительные цены и неверный OHLC отклоняются до расчёта как `invalid_market_data`. Пустая или короткая корректная история обрабатывается отдельно как недостаток данных.

Выходные и неторговые дни не дополняются искусственными свечами. Ожидаемые сессии определяет календарь инструмента, зафиксированный вместе со снимком. Пропуск ожидаемой сессии внутри доступной истории — ошибка данных; отсутствие истории до начала торгов нового инструмента — недостаток истории.

`position=flat` означает отсутствие акций, `position=long` — положительное число акций у движка. Количество акций и денежный остаток Tool не нужны: размер сделки рассчитывает BacktestEngine. Нельзя передавать желаемую позицию вместо фактической, например после покупки, которая не исполнилась из-за недостатка средств.

### Общие параметры сценария

Эти параметры проверяет вызывающий код ядра; они не включаются в `params` конкретной стратегии.

| Поле | Правило |
|---|---|
| `ticker` | Инструмент из каталога; валюта и положительный целый `lot_size` берутся из метаданных снимка |
| `period.start`, `period.end` | Включённые границы бэктеста; начало раньше конца, конец не позже текущей даты по календарю рынка, период не длиннее 3653 дней |
| `initial_capital` | Десятичная строка в валюте инструмента, от `1000.00` до `1000000000.00` включительно; по умолчанию `100000.00` |
| `commission_rate` | Десятичная строка, доля оборота одной сделки от 0 до 0.05; по умолчанию `0.0005`, то есть 0,05% |
| `history_window_bars` | Только текущий сигнал: целое число от 1 до 5000, не меньше минимума стратегии; правило значения по умолчанию — в разделе 7 |
| `snapshot_id` | Идентификатор неизменяемых свечей и метаданных; фиксируется до расчёта и возвращается в результате сценария |

Число JSON вместо денежной строки, неконечное значение и неверный формат отклоняются. Для денежных строк используется обычная десятичная запись без экспоненты; допустимы до 18 цифр целой части и до 10 после точки, затем проверяется диапазон конкретного поля. Капитал проверяется на границы до округления; нормализованное значение с точностью до копеек сохраняется в Job.

`history_window_bars` не ограничивает длительность бэктеста. В бэктесте используется выбранный период и прогрев; текущий сигнал проигрывает конечное окно без отдельного прогрева за его границами.

## 4. Результат одного вызова

| Поле ToolResult | Значение |
|---|---|
| `signal` | `BUY`, `SELL`, `HOLD` или `INSUFFICIENT_DATA` |
| `bar_time` | `close_time` последней переданной свечи; `null`, если история пуста |
| `reason.code` | Машиночитаемый код сработавшего правила |
| `reason.message` | Непустое пояснение для человека |
| `indicators` | Словарь рассчитанных значений десятичными строками; нерассчитанные значения — `null` |

- `BUY` — открыть длинную позицию; допустим при `position=flat`.
- `SELL` — закрыть длинную позицию; допустим при `position=long`.
- `HOLD` — сохранить позицию, включая отсутствие позиции. Это не обязательно «держать уже купленные акции».
- `INSUFFICIENT_DATA` — правило нельзя рассчитать. Это не приказ и не синоним `HOLD`.

Tool не возвращает цену исполнения, количество акций, комиссии, метрики или новое состояние Job. Движок не исполняет некорректный ответ: неизвестный сигнал, время другого бара, `BUY` при `long` или `SELL` при `flat` считаются нарушением контракта Tool и обрабатываются как `tool_failed`.

Пример SMA с `fast=2`, `slow=3`, позицией `flat` и первыми пятью свечами контрольного набора из раздела 11:

```json
{
  "signal": "BUY",
  "bar_time": "2026-11-06T18:00:00Z",
  "reason": {
    "code": "cross_up",
    "message": "Быстрая SMA пересекла медленную снизу вверх"
  },
  "indicators": {
    "fast_previous": "10",
    "slow_previous": "10",
    "fast_current": "13",
    "slow_current": "11.3333333333"
  }
}
```

Имена стратегии, версия, параметры, снимок и позиция добавляются к публичному ответу вызывающим сценарием. Они не вычисляются повторно из текста `reason.message`.

## 5. Две реализации за общим контрактом

### SMA crossover: `sma_crossover`, версия `1.0.0`

Схема параметров: [schemas/sma-crossover-params.schema.json](schemas/sma-crossover-params.schema.json).

| Параметр | Тип | По умолчанию | Ограничения |
|---|---|---|---|
| `fast` | Целое число | 20 | 1–499 |
| `slow` | Целое число | 50 | 2–500, обязательно `fast < slow` |

Неизвестные параметры запрещены. `{}` нормализуется в `{"fast": 20, "slow": 50}`. Строка `"20"`, `20.5` и `true` не принимаются вместо целого периода. Межполевое условие `fast < slow` проверяет `validate_params`, даже если отдельные поля прошли JSON Schema.

`SMA(n, t)` — среднее последних `n` цен закрытия по бар `t` включительно с одинаковым весом каждой свечи. Минимум истории — `slow + 1`: для пересечения нужны значения на текущем и предыдущем барах.

Цены читаются из строк снимка в `Decimal`. Последние `n` значений суммируются в хронологическом порядке и делятся на `n` в контексте 28 значащих цифр, `ROUND_HALF_EVEN`. Дополнительное округление промежуточных значений не применяется. Средние сравниваются непосредственно, без допуска. Скользящая оптимизация допустима только при совпадении с этим расчётом.

Для выдачи в `indicators` значения округляются до 10 знаков после точки через `ROUND_HALF_EVEN` и записываются десятичными строками. Округлённое представление не участвует в выборе сигнала; строки с `NaN` или бесконечностью запрещены.

Пересечение вверх: `fast_previous <= slow_previous` и `fast_current > slow_current`. Пересечение вниз: `fast_previous >= slow_previous` и `fast_current < slow_current`. Равенство текущих средних не считается пересечением.

| Условие | Позиция | `signal` | `reason.code` |
|---|---|---|---|
| Истории меньше `slow + 1` | Любая | `INSUFFICIENT_DATA` | `insufficient_history` |
| Пересечение вверх | `flat` | `BUY` | `cross_up` |
| Пересечение вверх | `long` | `HOLD` | `cross_up_while_long` |
| Пересечение вниз | `long` | `SELL` | `cross_down` |
| Пересечение вниз | `flat` | `HOLD` | `cross_down_while_flat` |
| Пересечения нет | Любая | `HOLD` | `no_cross` |

Проверка недостатка истории выполняется первой. `reason.message` поясняет соответствующую строку. При достаточной истории `indicators` содержит `fast_previous`, `slow_previous`, `fast_current`, `slow_current`. Если история началась уже с быстрой SMA выше медленной, покупка без нового пересечения не создаётся.

### Buy & hold: `buy_and_hold`, версия `1.0.0`

Схема параметров: [schemas/buy-and-hold-params.schema.json](schemas/buy-and-hold-params.schema.json). `params` — пустой объект `{}`; любые ключи запрещены. Минимум истории — один закрытый бар.

| Условие | Позиция | `signal` | `reason.code` |
|---|---|---|---|
| История пуста | Любая | `INSUFFICIENT_DATA` | `insufficient_history` |
| Есть закрытый бар | `flat` | `BUY` | `enter_baseline` |
| Есть закрытый бар | `long` | `HOLD` | `keep_baseline` |

`indicators` — пустой объект. `SELL` не выдаётся. Если покупка не исполнилась из-за недостатка денег, позиция остаётся `flat`, и на следующем баре стратегия снова может вернуть `BUY`.

Базовая линия использует те же капитал, комиссию, лоты, период и снимок, что и другие стратегии. Первый сигнал возникает на первом закрытом баре периода, а покупка — на следующем открытии. Покупка по первому закрытию или до начала периода не допускается.

## 6. Недостаток истории и прогрев

При нехватке баров Tool возвращает `INSUFFICIENT_DATA` с `reason.code=insufficient_history`. Пояснение указывает требуемое и фактическое число баров. Недоступные значения индикаторов не заменяются нулями.

В бэктесте такие бары не создают сделок. После накопления минимума обычные правила начинают работать. Если за весь период нет ни одного бара с достаточной историей, движок завершает расчёт ошибкой `insufficient_data`. Если история достаточна, но нет пересечений, денег на лот или следующего бара для исполнения, бэктест успешен и может содержать ноль сделок.

Перед бэктестом MarketDataService загружает `required_bars - 1` закрытых торговых баров до `period.start`: для SMA(20/50) — 50, для buy & hold — 0. Снимок включает прогрев. До начала периода сигналы не исполняются и позиция остаётся `flat`.

Для сравнения общий снимок содержит максимум необходимого прогрева всех стратегий. Каждая стратегия использует свой необходимый хвост прогрева и один и тот же период расчёта; лишние ранние бары другой стратегии не создают ей позицию до старта.

Если доступных баров прогрева меньше, используются все имеющиеся, а первые бары периода при необходимости дают `INSUFFICIENT_DATA`. При воспроизведении берутся только данные сохранённого снимка: прогрев не подменяется свежей загрузкой.

## 7. Текущий сигнал

`history_window_bars` — целое число последних закрытых свечей от 1 до 5000. Сначала нормализуются параметры стратегии и вычисляется `required_bars`, затем определяется окно:

| Запрос | Выбор окна |
|---|---|
| Поле не передано | `max(252, required_bars)` |
| Явно передано допустимое окно не меньше `required_bars` | Переданное значение |
| Явно передано меньше минимума | `invalid_params`, поле `history_window_bars`, причина `less_than_required_bars` |
| Тип неверен либо значение вне 1–5000 | `invalid_params`, причина `wrong_type` либо `out_of_range` |

Примеры: SMA(20/50) без окна — 252 бара; `slow=300` без окна — 301; `slow=500` без окна — 501. Явное окно 252 при `slow=300` отклоняется. Отсутствующее поле не создаёт ошибку из-за старого фиксированного значения по умолчанию.

Если реальной истории меньше запрошенного окна, проигрываются все доступные закрытые бары. Если их меньше минимума стратегии, результат — `INSUFFICIENT_DATA`, а не ошибка параметров и не `HOLD`. При пустой истории `bar_time=null`.

SignalService запускает движок от позиции `flat` с заданными капиталом и комиссией и возвращает решение последнего бара. Дополнительные бары за границами окна не используются. Последний сигнал не исполняется без следующего бара.

В публичном ответе есть стратегия с версией, нормализованные `params`, `signal`, `reason`, `indicators`, фактически выбранный `history_window_bars`, число использованных баров, `bar_time`, `snapshot_id` и `position`. Позиция добавляется движком после проигрывания окна, до исполнения последнего сигнала. Время формирования ответа не заменяет время рыночного бара и не влияет на результат Tool.

## 8. Исполнение, капитал и комиссии

### Исполнение сигнала

Движок поддерживает одну длинную позицию в одном инструменте, без заёмных средств, коротких позиций и частичных исполнений. Начальная позиция — `flat`, остаток — нормализованный `initial_capital`.

На каждом баре сначала исполняется сигнал предыдущего закрытия по текущему `open`, затем рассчитывается капитал на текущем закрытии и новый сигнал. Исполнение до закрытия сигнального бара запрещено. Без следующего торгового бара сигнал сохраняется, но сделки нет.

`BUY` приобретает максимум целых лотов с учётом округлённой комиссии; `SELL` продаёт всю позицию. С `HOLD`, `INSUFFICIENT_DATA` и неисполненного сигнала комиссия не взимается. Отсутствие денег на лот не превращается в ошибку стратегии: сделки нет и позиция остаётся `flat`.

### Денежная арифметика

Расчёты используют `Decimal` с точностью 28 значащих цифр, `ROUND_HALF_EVEN`; денежное округление до копеек отдельно выполняется через `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. `cash`, включая начальный капитал, хранится с двумя знаками. Округлённый начальный капитал сохраняется вместе с параметрами запуска.

При цене открытия `p`, остатке `cash`, числе акций в лоте `L` и ставке `r`:

```text
quantity_preliminary = floor(cash / (L * p * (1 + r))) * L
commission(quantity) = round_half_up(quantity * p * r, 0.01)
```

Предварительное количество корректируется до максимального неотрицательного `quantity`, кратного `L`, для которого `quantity * p + commission(quantity) <= cash`. Если округление комиссии вверх мешает покупке, количество уменьшается на целые лоты; если округление вниз позволяет докупить лоты, оно увеличивается. При поиске числа лотов частное не округляется вверх из-за ограниченной точности `Decimal`.

После исполнения:

```text
BUY:  cash_after = round_half_up(cash - quantity * p - commission(quantity), 0.01)
SELL: cash_after = round_half_up(cash + quantity * p - commission(quantity), 0.01)
```

Комиссия округляется отдельно для каждой исполненной операции. Округлённые индикаторы не используются для расчёта денег, а отображаемые проценты — для повторного вычисления метрик. Правила одинаковы для стратегий и базовой линии.

### Результаты бэктеста

В конце периода принудительной продажи нет. Открытая позиция оценивается по последнему `close`; капитал на закрытии бара равен `cash + quantity * close`, общая доходность — `equity_last / initial_capital - 1`.

Движок формирует кривую капитала, просадку, Шарп и статистику сделок. Для статистики прибыльности позиция закрывается продажей; открытая позиция участвует в капитале, но не считается закрытой. Tool не реализует собственные формулы метрик или правила комиссии.

## 9. Ошибки и негативные случаи

Доменная ошибка передаёт `code`, `message`, `details.field` и `details.reason`. HTTP-слой добавляет оболочку и correlation ID; JobRunner сохраняет ошибку выполнения в задании и вызывает JobLifecycle. Это разные способы доставки одной причины, а не обязанность Tool управлять HTTP и Job.

Пример ошибки параметров в публичном формате:

```json
{
  "error": {
    "code": "invalid_params",
    "message": "fast должен быть меньше slow",
    "details": {"field": "params.fast", "reason": "must_be_less_than_slow"},
    "correlation_id": "c0a8012e-5f1d-4c2b-9e3a-7b6d8f9e0a11"
  }
}
```

| Код | Кто обнаруживает | Последствие |
|---|---|---|
| `invalid_params` | `validate_params` для параметров Tool, входной сценарий для общих полей | До создания Job — отказ; при прямом обращении к ядру — явная ошибка с полем и причиной |
| `unknown_operation` | Registry при выборе неизвестной стратегии | Job не создаётся |
| `invalid_market_data` | MarketDataService перед расчётом | Данные не поступают в Tool; задание завершается ошибкой |
| `insufficient_data` | BacktestEngine | В периоде бэктеста нет ни одного пригодного бара; для текущего сигнала применяется результат `INSUFFICIENT_DATA` |
| `tool_failed` | Dispatcher при исключении либо при обнаружении некорректного результата Tool | Ответ не исполняется, задание завершается ошибкой |
| `strategy_unavailable` | JobRunner при проверке сохранённой версии | Задание нельзя начать; версия не заменяется текущей |

Сетевые таймауты, аренда worker и потеря снимка относятся к MarketDataService, JobRunner и хранилищу, а не к StrategyTool. Их жизненный цикл и транспортные коды описываются архитектурой и API.

| Вход или ситуация | Поле | Причина / результат |
|---|---|---|
| `fast=0` или вне диапазона | `params.fast` | `out_of_range` |
| `fast=true`, `fast="20"`, `fast=20.5` | `params.fast` | `wrong_type` |
| `fast >= slow` после подстановки значений по умолчанию | `params.fast` | `must_be_less_than_slow` |
| Неизвестный ключ `extra` в параметрах | `params.extra` | `unknown_field` |
| Непустые параметры buy & hold | Путь к неизвестному ключу | `unknown_field` |
| Параметры не объект | `params` | `wrong_type` |
| Капитал или комиссия вне допустимого диапазона | `initial_capital` / `commission_rate` | `out_of_range` |
| Явное окно меньше минимума | `history_window_bars` | `less_than_required_bars` |
| Корректная, но короткая история | — | `INSUFFICIENT_DATA`, сделок нет |
| Дубль свечи, нулевая цена или неверный OHLC | Путь к свече или цене | `invalid_market_data` |

Текст сообщения помогает человеку, клиент проверяет код и причину. В комбинированном запросе путь может иметь префикс `strategies[1].params.fast`: входной сценарий добавляет контекст элемента сравнения к ошибке Tool.

Поздний ответ после отмены или завершения не сохраняется как новый результат: состояние и право записи проверяет JobLifecycle. Повтор запуска — новый Job; Tool не переводит старое задание обратно в работу.

## 10. Воспроизводимость и расширение

Для воспроизведения сохраняются неизменяемый снимок свечей и метаданных инструмента, его календарь и прогрев, период или окно, нормализованные параметры, капитал, комиссия, версия стратегии и `engine_version`. На одинаковых входах сигналы, сделки и метрики совпадают. Совпадения только тикера, периода и `snapshot_id` без совпадения версий недостаточно.

Tool не использует случайность, системное время, глобальную позицию и изменяемые внешние данные. Префикс истории даёт то же решение независимо от наличия будущих баров в исходном снимке. Сам снимок не изменяется после расчёта; новый набор данных получает новый идентификатор.

Registry регистрирует Tool под уникальной парой `(name, version)`. Новая версия нужна при изменении торговых правил, схемы или значений параметров по умолчанию, арифметики индикаторов либо смысла результата. Изменение исполнения, комиссии или формулы метрик отражается в версии движка.

Добавление стратегии:

1. Реализовать общий интерфейс, схему параметров и правило `required_bars`.
2. Зарегистрировать Tool в месте сборки приложения; дублирующая пара имени и версии отклоняется.
3. Проверить обычный сигнал, ошибки параметров, недостаток истории и одинаковый результат на фиксированном снимке.

Каталог получает данные из Tool, Dispatcher выбирает его по сохранённым имени и версии. В Dispatcher не появляются условия по `sma_crossover`, `buy_and_hold` или новому имени. Другая стратегия использует ту же модель исполнения; изменение этой модели — изменение контракта движка, а не скрытая особенность одного Tool.

## 11. Контрольные примеры

Машиночитаемые данные: [examples/strategy-tool-cases.json](examples/strategy-tool-cases.json). В файле искусственный инструмент `TEST`, календарь из семи сессий, параметры, ожидаемые сигналы и причины, исполнения, негативные случаи, окна и границы округления комиссии. Календарь не описывает реальные торговые дни Московской биржи.

Для обеих стратегий: капитал `1000.00`, комиссия `0.001`, лот 10 акций, семь цен закрытия `10, 10, 8, 12, 14, 6, 7`. До первой свечи истории нет, поэтому доступный прогрев — 0.

| Проверка | SMA(2/3) | Buy & hold |
|---|---|---|
| Первая возможность рассчитать сигнал | Четвёртый бар, средние равны — `HOLD` | Первый бар — `BUY` |
| Покупка | `BUY` на пятом закрытии, 60 акций на шестом открытии по 15 | 90 акций на втором открытии по 10 |
| Комиссия покупки | `0.90`, остаток `99.10` | `0.90`, остаток `99.10` |
| Продажа | `SELL` на шестом закрытии, 60 акций на седьмом открытии по 7; комиссия `0.42` | Не продаёт |
| Конечные акции / деньги | 0 / `518.68` | 90 / `99.10` |
| Конечный капитал | `518.68` | `729.10` |
| Общая доходность | `-0.48132`, то есть −48,132% | `-0.2709`, то есть −27,09% |

Дополнительные вызовы на том же снимке проверяют `cross_up_while_long`, `cross_down_while_flat`, равенство средних и пустую историю. Границы комиссии проверяются в обе стороны: округление вверх не даёт потратить больше остатка, округление вниз не мешает купить доступный целый лот.
