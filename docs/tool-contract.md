# Контракт StrategyTool

Контракт описывает стратегии TradeLab для практики 2. Сценарии — в [requirements.md](requirements.md), назначение сервиса — в [concept.md](concept.md).

## 1. Ответственность и интерфейс

`StrategyTool` рассчитывает индикаторы и выдаёт сигнал на закрытом баре. Общий движок исполняет сигналы, учитывает капитал и комиссии, формирует сделки и метрики. Поэтому список сигналов и сделок из концепции — результат совместной работы стратегии и движка.

Общий интерфейс всех стратегий:

```text
name                                      — имя стратегии
version                                   — версия правил стратегии и значений по умолчанию
params_schema() → JSON Schema параметров   — типы, диапазоны и значения по умолчанию для каталога
validate_params(params) → normalized_params или ToolError
required_bars(normalized_params) → минимальное число баров
execute(closed_bars, position, normalized_params) → ToolResult или ToolError
```

Стратегия не меняет Job и позицию, не загружает котировки и не обращается к БД. `position` — фактическое состояние позиции движка: `flat` или `long`.

## 2. Вход и результат

`closed_bars` — упорядоченная история закрытых дневных свечей до текущего бара включительно. Свеча содержит время закрытия, `open`, `high`, `low`, `close`, `volume`. Цены — положительные конечные числа; дубли, неверный OHLC и незакрытые свечи отклоняются вызывающим кодом до обращения к Tool.

`params` — объект параметров выбранной стратегии. `validate_params` соответствует `params_schema()`: проверяет типы, диапазоны и отсутствие неизвестных ключей, подставляет те же значения по умолчанию. Связи полей, например `fast < slow`, проверяются дополнительно в `validate_params`. Например, строка `"20"`, число `20.5` и `true` не принимаются вместо целого периода. Проверку вызывает входной сценарий ядра до создания Job; она обязательна и при обращении к ядру без HTTP.

`ToolResult` содержит:

| Поле | Значение |
|---|---|
| `signal` | `BUY`, `SELL`, `HOLD` или `INSUFFICIENT_DATA` |
| `bar_time` | Время закрытия последнего использованного бара; `null`, если история пуста |
| `reason` | Код и пояснение сработавшего правила |
| `indicators` | Рассчитанные значения индикаторов десятичными строками; недоступные значения — `null` |

`BUY` означает открыть длинную позицию при `flat`, `SELL` — закрыть её при `long`, `HOLD` — сохранить текущую позицию, включая отсутствие позиции. Tool не возвращает цену исполнения, количество акций, комиссии или метрики: это ответственность движка.

## 3. Две реализации

### `sma_crossover`, версия `1.0.0` — пересечение скользящих средних

| Параметр | Тип | По умолчанию | Ограничение |
|---|---|---|---|
| `fast` | Целое число | 20 | 1–499 |
| `slow` | Целое число | 50 | 2–500, обязательно `fast < slow` |

SMA — среднее последних цен закрытия с одинаковым весом каждой свечи. Минимум истории — `slow + 1` баров: нужны средние на текущем и предыдущем барах. Цены читаются из десятичных строк снимка в `Decimal`; значения суммируются в хронологическом порядке. Контекст расчёта — 28 значащих цифр, `ROUND_HALF_EVEN`. Средние сравниваются непосредственно, без допуска и дополнительного округления. При выдаче в `indicators` значения округляются до 10 знаков после точки тем же способом; это представление не участвует в выборе сигнала.

Пересечение вверх: на предыдущем баре `SMA_fast <= SMA_slow`, на текущем `SMA_fast > SMA_slow`. Пересечение вниз: на предыдущем баре `SMA_fast >= SMA_slow`, на текущем `SMA_fast < SMA_slow`. Равенство текущих средних не считается пересечением.

| Условие | Позиция | `signal` | `reason.code` |
|---|---|---|---|
| Пересечение вверх | `flat` | `BUY` | `cross_up` |
| Пересечение вверх | `long` | `HOLD` | `cross_up_while_long` |
| Пересечение вниз | `long` | `SELL` | `cross_down` |
| Пересечение вниз | `flat` | `HOLD` | `cross_down_while_flat` |
| Пересечения нет | Любая | `HOLD` | `no_cross` |

`reason.message` поясняет соответствующую строку таблицы. В `indicators` возвращаются `fast_previous`, `slow_previous`, `fast_current`, `slow_current`. При недостатке истории сначала применяется правило из раздела 4.

### `buy_and_hold`, версия `1.0.0` — «купить и держать»

`params` — пустой объект `{}`; неизвестные параметры запрещены. Минимум истории — один закрытый бар.

- При `flat` возвращается `BUY` с причиной `enter_baseline`.
- При `long` возвращается `HOLD` с причиной `keep_baseline`.
- `SELL` не выдаётся; `indicators` — пустой объект.

Обе стратегии используют одинаковые вход, формат результата, проверку параметров и ошибки.

## 4. Недостаток данных и ошибки

Если история короче `required_bars`, обе стратегии возвращают `INSUFFICIENT_DATA` с причиной `insufficient_history`, требуемым и фактическим количеством баров в пояснении. Это не `HOLD`: приказ на сделку не создаётся. В бэктесте такие бары пропускаются; если за весь период нет ни одного пригодного для расчёта бара, задание завершается ошибкой `insufficient_data`. Текущий сигнал при короткой истории остаётся `INSUFFICIENT_DATA`.

`ToolError` передаёт `code`, `message` и `details` с полем и причиной. Пример ошибки SMA:

```json
{
  "error": {
    "code": "invalid_params",
    "message": "fast должен быть меньше slow",
    "details": {"field": "params.fast", "reason": "must_be_less_than_slow"}
  }
}
```

| Ошибка | Кто обнаруживает | Пример |
|---|---|---|
| `invalid_params` | `Tool.validate_params` для параметров стратегии; вызывающий код для общих параметров | `params.fast`: `wrong_type`, `out_of_range`, `must_be_less_than_slow`; неизвестное поле: `unknown_field` |
| `unknown_operation` | Registry до выбора Tool | Имя стратегии отсутствует |
| `invalid_market_data` | Вызывающий код до расчёта | Дубли свечей, нулевая цена, неверный OHLC |
| `tool_failed` | Dispatcher при неожиданном исключении Tool | Выполнение стратегии завершилось исключением |

Первые две ошибки при проверке запроса не создают Job. Ошибка при выполнении переводит ещё выполняющийся Job в `failed`; отменённое или завершённое задание поздним ответом Tool не изменяется. HTTP-коды задаются отдельно в контракте API.

## 5. Капитал и исполнение

Общие параметры проверяет движок: `initial_capital` — сумма в валюте инструмента от `1000.00` до `1000000000.00` включительно, по умолчанию `100000.00`; `commission_rate` — доля оборота сделки от 0 до 0.05, по умолчанию `0.0005` (0,05%). За пределами диапазона — `invalid_params` с соответствующим полем и причиной `out_of_range`; неконечные значения запрещены. В API обе величины передаются десятичными строками и читаются как `Decimal`.

В MVP используется одна длинная позиция без заёмных средств. Размер покупки — максимум целых лотов на доступные деньги с учётом комиссии. При остатке `cash`, цене открытия `p`, размере лота `L` и комиссии `r`:

```text
quantity = floor(cash / (L * p * (1 + r))) * L
commission = round_half_up(quantity * p * r, 0.01)
```

Формула даёт предварительное количество. После округления комиссии движок проверяет `quantity * p + commission <= cash`; если денег не хватает, уменьшает количество на один лот и пересчитывает комиссию до выполнения условия. Если округление комиссии вниз позволяет купить дополнительные лоты, количество увеличивается до максимального, удовлетворяющего тому же неравенству. Денежный остаток, включая начальный капитал, округляется до копеек через `Decimal.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`; нормализованный начальный капитал сохраняется в задании. При покупке остаток уменьшается на стоимость акций и комиссию, при продаже увеличивается на выручку за вычетом комиссии и затем округляется тем же способом.

Если денег не хватает на лот, сделка не создаётся и позиция остаётся `flat`. `SELL` закрывает всю позицию. Комиссию считает движок с каждой исполненной покупки и продажи; с `HOLD` комиссия не взимается. Начальная позиция — `flat`; в конце периода принудительной продажи нет, открытая позиция оценивается по последнему закрытию.

Сигнал на баре `t` использует только данные, известные к его закрытию. Движок передаёт Tool только этот префикс истории и исполняет сигнал не раньше открытия следующего торгового бара. В MVP цена исполнения — его `open`. Без следующего бара сигнал сохраняется, но сделка не создаётся.

Для бэктеста MarketDataService загружает `required_bars - 1` закрытых торговых баров до начала выбранного периода: для SMA(20/50) — 50, для buy & hold — 0. Снимок включает этот прогрев; для сравнения используется максимум по всем стратегиям сравнения. До начала периода сигналы не исполняются, позиция остаётся `flat`. Если доступных баров прогрева меньше, используются все имеющиеся, а первые бары периода при необходимости дают `INSUFFICIENT_DATA` по разделу 4.

## 6. Текущий сигнал и воспроизводимость

Для текущего сигнала используется `history_window_bars`: целое число последних закрытых свечей от 1 до 5000. Если поле не передано, после нормализации параметров стратегии выбирается `max(252, required_bars)`: для SMA с `slow=300` это 301 бар. Явно переданное окно меньше `required_bars` отклоняется как `invalid_params` с полем `history_window_bars` и причиной `less_than_required_bars`; выход за диапазон 1–5000 — с причиной `out_of_range`. Если окно допустимо, но реальной истории меньше минимума, Tool возвращает `INSUFFICIENT_DATA`.

Движок проигрывает выбранное окно от позиции `flat` с указанными капиталом и комиссией и возвращает сигнал последнего бара. В ответе указываются фактически выбранный размер окна, время последнего бара, `snapshot_id` и `position`: позиция после проигрывания окна, до исполнения текущего сигнала. Её добавляет движок, а не Tool. Для бэктеста используется выбранный период с прогревом, а не ограничение в 252 бара.

Для воспроизведения сохраняются неизменяемый снимок свечей и метаданных инструмента, период или окно, нормализованные параметры, начальный капитал, комиссия, версии стратегии и движка. На одинаковых входах сигналы, сделки и метрики совпадают. Tool не использует случайность и системное время; денежные расчёты выполняет общий движок в десятичной арифметике.

## 7. Добавление стратегии

Новый Tool реализует тот же интерфейс и регистрируется в Registry под уникальной парой `(name, version)`. Смена правил расчёта или значений по умолчанию требует новой версии. Каталог получает схему параметров через `params_schema()`, а выбранная версия сохраняется в Job. Dispatcher получает Tool по сохранённым имени и версии и вызывает общий интерфейс: условия по конкретным именам стратегий в Dispatcher не добавляются. Меняются реализация и регистрация, а не управляющая логика.
