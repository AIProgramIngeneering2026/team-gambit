# ADR 0001. Модель выполнения заданий и восстановление после перезапуска

- **Дата:** 2026-11-14
- **Статус:** принято
- **Связанные документы:** [architecture.md](../architecture.md), [requirements.md](../requirements.md#жизненный-цикл-job), [concept.md](../concept.md)

## Контекст

Бэктест выполняется асинхронно: пользователь создаёт задание (`BacktestJob`), а результат забирает позже. Модель выполнения должна обеспечить требования из концепции и сценариев:

- задание проходит жизненный цикл `created → queued → running → completed / failed / canceled`, недопустимые переходы отклоняются, терминальные состояния не изменяются;
- после перезапуска worker не теряет задания в очереди и не берёт чужие;
- повторный запуск любого этапа не создаёт дубликатов заданий и результатов;
- недоступность поставщика данных переводит одно задание в `failed` и не влияет на остальные;
- отмена разрешена в том числе во время выполнения, и у отменённого задания не бывает результата;
- нет заданий, завершившихся ошибкой без диагностируемой причины.

Ограничения MVP: один пользователь или небольшая команда, дневные свечи, бэктест типового периода занимает секунды, нагрузка — единицы заданий в минуту. Хранилище — PostgreSQL, на прототипе — SQLite с теми же миграциями. Команда из трёх человек, поддерживать отдельную инфраструктуру очередей нецелесообразно.

## Решение

### Процессы и очередь

1. **Два типа процессов:** HTTP API и worker (один или несколько экземпляров). API не выполняет бэктесты, worker не принимает HTTP-запросы.
2. **Очередь — таблица заданий в основной БД.** Поставить задание в очередь значит перевести его в `queued`. Отдельного брокера сообщений нет. API и worker общаются только через БД.
3. **Создание задания** — одна транзакция: проверка ключа идемпотентности (уникальный индекс), вставка Job в `created`, переход `created → queued`, две записи в `JobStatusHistory`. Повтор запроса с тем же ключом возвращает существующее задание.
4. **Захват задания** — одна короткая транзакция:
   1. выбрать самое старое задание в `queued` (в PostgreSQL — `FOR UPDATE SKIP LOCKED`, чтобы worker не ждали друг друга; в SQLite запись и так последовательна);
   2. проверить, что его можно начать: стратегия с нужной версией есть в Registry, снимок для повторного запуска существует;
   3. выполнить compare-and-set: при успешной проверке — `queued → running`, иначе — `queued → failed` с кодом `strategy_unavailable` или `snapshot_not_found`.

   ```sql
   UPDATE backtest_job
      SET state = 'running', worker_id = :worker_id,
          lease_expires_at = now() + :lease, deadline_at = now() + :job_timeout
    WHERE id = :id AND state = 'queued';
   ```

   Если строка не обновилась, задание уже отменено или взято другим worker, и этот worker пробует следующее.
5. **Каждый экземпляр worker выполняет одно задание за раз.** Масштабирование — числом процессов.

### Аренда и сроки

6. Worker держит задание по **аренде**: продлевает `lease_expires_at` heartbeat-ом (`UPDATE … WHERE id = :id AND state = 'running' AND worker_id = :worker_id`). Если строка не обновилась, задание отменено или отобрано, и worker прекращает его обработку.
7. У задания есть **срок выполнения** `deadline_at`. Dispatcher проверяет его между вызовами Tool.
8. **Reaper** работает в каждом экземпляре worker и периодически переводит в `failed` задания `running`, у которых истекла аренда (`worker_lost`) или срок выполнения (`job_timeout`).
9. Все сроки считаются по часам БД (`now()`), а не по часам worker.
10. Значения по умолчанию задаются переменными окружения: опрос очереди — каждую 1 с, аренда — 30 с, heartbeat — каждые 10 с, проверка Reaper — каждые 10 с, срок выполнения — 5 мин.

### Переходы и результат

11. Любой переход состояния выполняет JobLifecycle: проверка по таблице разрешённых переходов, затем compare-and-set по ожидаемому исходному состоянию (для переходов worker — и по `worker_id`) и запись в историю в одной транзакции.
12. Результат и сделки сохраняются **только** в транзакции перехода `running → completed`; код и описание ошибки — только в транзакции перехода в `failed`. Если compare-and-set не прошёл, ничего не сохраняется, а событие пишется в лог (`stale_transition`, `late_result_discarded`).
13. Внутри одного Job автоматического повтора нет: переходов `running → queued` в модели нет. Упавшее задание пользователь повторяет новым Job (`rerun_of` ссылается на исходное).

### Восстановление после перезапуска

| Что перезапустилось | Что происходит |
|---|---|
| Процесс API | Состояния в памяти нет. Запрос, оборвавшийся до фиксации транзакции, не оставил следов; клиент повторяет его с тем же ключом идемпотентности и получает одно задание. |
| Worker во время задания | Аренда истекает, Reaper другого экземпляра (или этого же после старта) переводит задание в `failed` с `worker_lost`. Задания в `queued` остаются в БД и захватываются любым живым worker. |
| Worker при штатной остановке (SIGTERM) | Worker перестаёт захватывать новые задания и дожидается текущего в пределах срока выполнения; если не успел — выходит, задание завершит Reaper. |
| Перезапущенный worker | Получает новый `worker_id`, поэтому не может продолжить прежние задания и не может завершить чужие: его compare-and-set по `worker_id` не пройдёт. |
| Worker, который «потерялся» и вернулся | Его heartbeat и запись результата не проходят compare-and-set; результат отбрасывается как поздний ответ. |
| БД | Незафиксированные транзакции откатываются, зафиксированные состояния и история сохранены. Worker и API повторяют подключение; задания `running` с истёкшей арендой завершит Reaper. |
| Вся система | Задания `created` не наблюдаются (постановка в той же транзакции), `queued` выполняются после старта worker, зависшие `running` уходят в `failed` с `worker_lost`. Задание не может остаться «вечно в работе». |

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| **Выполнение внутри процесса API** (FastAPI `BackgroundTasks`, пул потоков) | Задания пропадают при перезапуске API, тяжёлый расчёт делит ресурсы с обработкой запросов, нельзя масштабировать исполнителей отдельно. Противоречит требованию «не терять задания после перезапуска». |
| **Брокер сообщений** (Redis/RabbitMQ + Celery или RQ) | Два источника истины — состояние в БД и сообщение в очереди: нужно согласовывать их при сбоях (outbox или двойная запись), а гарантия «at least once» всё равно требует идемпотентности и fencing на стороне БД. Дополнительная инфраструктура для команды из трёх человек при нагрузке в единицы заданий в минуту. |
| **Автоматический повтор внутри того же Job** (переход `running → queued` после потери worker) | Требует нового перехода в согласованной модели состояний и счётчика попыток; при повторе на новом снимке результат перестаёт быть однозначно связан с заданием. Бэктест занимает секунды, поэтому ручной повтор новым Job дешевле, а история остаётся честной. |
| **Отмена через флаг `cancel_requested` и промежуточное состояние «отменяется»** | Ещё одно состояние и переход в согласованной модели; пользователь дольше видит неокончательное состояние. Прямой переход `running → canceled` с compare-and-set даёт тот же результат: поздний ответ worker отбрасывается. |
| **Блокировка задания на всё время выполнения** (`SELECT … FOR UPDATE` в долгой транзакции) | Долгие транзакции держат соединения и блокировки, не работают в SQLite, при обрыве соединения статус «в работе» нигде не виден. Аренда с явным сроком наблюдаема и переживает перезапуск. |

## Цена решения

- **Задержка старта.** Worker опрашивает БД, поэтому задание начинается с задержкой до интервала опроса (по умолчанию 1 с). Для бэктестов, которые идут секунды, это приемлемо.
- **Нагрузка на БД.** Опрос, heartbeat и Reaper — постоянный фоновый поток запросов. При единицах worker он незаметен, но растёт линейно с числом экземпляров.
- **Ложный `worker_lost`.** Если worker жив, но не смог продлить аренду (пауза сети, долгая сборка мусора), его задание уйдёт в `failed`, а готовый результат будет отброшен. Пользователю придётся повторить запуск.
- **Задержка обнаружения падения.** Задание упавшего worker остаётся в `running` до истечения аренды и следующей проверки Reaper — до ~40 с при значениях по умолчанию.
- **Отмена не мгновенно останавливает расчёт.** Состояние меняется сразу, но worker узнаёт об отмене на ближайшем heartbeat или записи; до этого он тратит ресурсы впустую.
- **Нет автоматических повторов.** Временный сбой поставщика данных требует от пользователя повторного запуска.
- **SQLite на прототипе** не поддерживает `SKIP LOCKED` и сериализует запись; параллельные worker на SQLite будут конкурировать за блокировку.

## Условия пересмотра

Решение пересматривается, если выполняется хотя бы одно из условий:

- типичный бэктест длится дольше срока аренды или минут — понадобятся промежуточные контрольные точки и автоматический повтор;
- доля заданий с `worker_lost` или `job_timeout` превышает 1% за неделю;
- поток заданий вырастает до сотен в минуту или опрос заметно нагружает БД (p95 захвата задания больше 100 мс) — рассмотреть `LISTEN/NOTIFY` или брокер сообщений;
- нужна задержка старта меньше секунды;
- нужен автоматический повтор при временном сбое поставщика данных — потребуется переход `running → queued` и согласование модели состояний в [requirements.md](../requirements.md#жизненный-цикл-job);
- появляются задания, которые нельзя выполнить одним worker (портфели, оптимизация параметров), или отказ от единой БД.
