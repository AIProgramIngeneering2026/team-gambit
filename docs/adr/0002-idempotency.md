# ADR 0002. Идемпотентность создания заданий

- **Дата:** 2026-11-14
- **Статус:** принято
- **Связанные документы:** [openapi.yaml](../api/openapi.yaml), [ADR 0001](0001-execution-model.md), [architecture.md](../architecture.md), [requirements.md](../requirements.md#с1-запуск-бэктеста-и-получение-результата-основной)

## Контекст

Задание на бэктест создаётся HTTP-запросом, и этот запрос может прийти больше одного раза:

- пользователь дважды нажал кнопку, и клиент отправил два одинаковых запроса с разницей в 100 мс;
- сервер создал задание, но ответ потерялся (таймаут соединения, перезапуск API), и клиент повторяет запрос, не зная, создано ли задание;
- два одинаковых запроса пришли одновременно в разные экземпляры API.

Требования:

- повтор с тем же ключом возвращает то же задание и не создаёт дубликат (С1, [concept.md](../concept.md) 7.2);
- повторный запуск любого этапа не создаёт дубликатов заданий и результатов (concept.md, раздел 11);
- намеренный повтор того же бэктеста допустим: С1 требует, чтобы два одинаковых задания на одном снимке дали одинаковый результат, поэтому одинаковые параметры сами по себе не дубль.

Ограничения:

- по [ADR 0001](0001-execution-model.md) API и worker общаются только через БД, создание задания — одна короткая транзакция, отдельного брокера и Redis нет;
- проверка запроса локальная: каталог стратегий (Registry) и список инструментов не требуют обращения к поставщику данных, поэтому транзакция создания не ждёт внешних вызовов;
- задания создают три операции: `POST /jobs`, `POST /jobs/{job_id}/rerun` и `POST /comparisons`;
- клиентов немного (MVP — один пользователь или небольшая команда), у каждого свой `X-API-Key`.

## Решение

### Ключ

1. Операции, которые создают задания, требуют заголовок `Idempotency-Key`. Без него — `400 missing_idempotency_key`, ключ неверного формата — `400 invalid_idempotency_key`. Остальные операции ключ не используют: чтение не меняет состояние, `POST /signal` не создаёт ресурсов, повтор отмены отвечает `409 job_state_conflict` с `current_state: canceled`.
2. Ключ — строка от 1 до 64 символов `[A-Za-z0-9_-]`, рекомендуется UUID v4. Клиент создаёт его один раз на действие пользователя (например, при открытии формы запуска) и передаёт при каждом повторе этого действия. Новое действие — новый ключ.
3. Ключ действует в пределах клиента: уникальна пара `(client_id, key)`. Разные клиенты с одинаковыми ключами друг другу не мешают и не видят ресурсов друг друга.

### Отпечаток запроса

4. С ключом сохраняется отпечаток запроса — SHA-256 от метода, пути (для `rerun` — вместе с id исходного задания) и канонического JSON тела: ключи отсортированы, незначащие пробелы удалены, значения такие, как прислал клиент.
5. Отпечаток считается до проверки параметров. Поэтому повтор находит прежнее задание, даже если с тех пор изменился каталог: стратегию сняли с регистрации или поменяли значения по умолчанию.

### Обработка запроса

6. Порядок: ключ клиента, размер тела и разбор JSON, формат ключа, поиск ключа, проверка параметров, лимит активных заданий, создание.
7. Ключ найден, не истёк и отпечаток совпал — ответ `200` с **текущим** состоянием того же ресурса и заголовком `Idempotent-Replayed: true`. Проверка параметров и лимиты не выполняются, новое задание не создаётся. Это верно для ресурса в любом состоянии: повтор запроса упавшего задания не перезапускает его — для этого есть `rerun` с новым ключом.
8. Ключ найден, отпечаток другой — `409 idempotency_key_reused`, в `details` — поле `Idempotency-Key` и id существующего задания.
9. Ключ не найден — проверка параметров и лимита. Отказ `422` или `429` ключ не занимает: исправленный запрос можно отправить с тем же ключом.
10. Создание — одна транзакция: запись ключа `(client_id, key, fingerprint, resource_type, resource_id, expires_at)`, задание (или все задания сравнения) в `queued`, записи истории состояний. Первый ответ — `202 Accepted` с заголовком `Location`.

### Одновременные запросы

11. Уникальный индекс `(client_id, key)` в таблице ключей. Два одновременных запроса не находят ключ, оба проходят проверку и пытаются вставить запись. БД фиксирует одну транзакцию, вторая получает нарушение уникальности (PostgreSQL ждёт завершения первой транзакции; в SQLite запись и так последовательна), откатывается целиком без задания, перечитывает запись ключа и отвечает как повтор: `200` или `409`, если отпечаток другой.
12. Состояния ключа «запрос в обработке» нет: транзакция создания короткая и без внешних вызовов, а до её фиксации ни ключа, ни задания не существует.

### Срок хранения

13. Ключ действует 24 часа с момента создания (`expires_at` по часам БД). Поиск учитывает только неистёкшие ключи. Истёкшая запись с тем же ключом удаляется в транзакции создания перед вставкой новой, остальные — периодической очисткой раз в час.
14. После истечения срока тот же ключ создаёт новый ресурс. Задание хранит свой ключ для диагностики, но в API его не возвращает.

### Что отвечает клиенту

| Ситуация | Ответ |
|---|---|
| Двойной клик, оба запроса с одним ключом | Одно задание; первый — `202`, второй — `200` с тем же `id` |
| Ответ потерялся, клиент повторил в течение 24 часов | `200` с тем же заданием в текущем состоянии |
| Ответ потерялся до фиксации транзакции | Задания нет, повтор создаёт его — `202` |
| Тот же ключ, другие параметры | `409 idempotency_key_reused` |
| Тот же ключ после ошибки валидации | Обрабатывается как новый запрос |
| Повтор через сутки | Новое задание |

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| **Без ключа: дубликат определяется по совпадению параметров за окно времени** | Намеренный повтор того же бэктеста (С1, проверка воспроизводимости) был бы отклонён. Окно выбирается произвольно: повтор после долгого обрыва связи выходит за окно и создаёт дубль. |
| **Необязательный ключ** | Клиент, который забыл ключ, снова получает дубли при двойном клике. Защита должна работать по умолчанию. |
| **Идентификатор задания от клиента** (`PUT /jobs/{id}`) | Идемпотентность естественная, но клиент управляет идентификаторами ресурсов: возможны коллизии и предсказуемые id, а модель «чужой id неотличим от несуществующего» усложняется. Для `rerun` и сравнений понадобились бы свои схемы. |
| **Ключ в теле запроса** | Смешивает транспортный механизм с параметрами бэктеста и меняет отпечаток тела. Заголовок `Idempotency-Key` — распространённая практика (черновик IETF «The Idempotency-Key HTTP Header Field»). |
| **Отпечаток по нормализованным параметрам** (после `validate_params` и подстановки значений по умолчанию) | Требует проверки до поиска ключа: повтор после изменения каталога получил бы `422` или `409` вместо прежнего задания. Нормализация зависит от версии стратегии, и клиенту сложнее понять, почему два запроса считаются разными. |
| **Хранение ключей в Redis с TTL** | Отдельная инфраструктура и второй источник истины. Запись ключа нельзя сделать атомарной с созданием задания в БД, а ADR 0001 оставляет БД единственным каналом. |
| **Бессрочное хранение, ключ — колонка задания** | Таблица растёт без ограничений, ключ нельзя использовать повторно. Для сравнений и `rerun` нужны были бы такие же колонки в других таблицах. |
| **Возвращать сохранённый первоначальный ответ** (как Stripe) | Нужно хранить тела ответов. После обрыва связи клиенту важнее текущее состояние задания, чем копия ответа на момент создания. |
| **Состояние ключа «в обработке» и ответ `409` на одновременный повтор** | Нужно, когда создание долгое или зовёт внешние сервисы. У нас транзакция короткая, и уникальный индекс решает гонку без дополнительного состояния. |

## Цена решения

- **Клиент обязан создавать и хранить ключ.** Запрос без ключа отклоняется — ручные запросы через `curl` требуют лишнего заголовка.
- **Ключ привязан к тексту запроса, а не к смыслу.** Тот же бэктест с явно указанным значением по умолчанию — другой отпечаток и `409`. Клиент должен повторять тот же JSON; порядок ключей и пробелы значения не имеют.
- **Окно 24 часа.** Повтор позже создаст второе задание; ключ после истечения можно использовать снова.
- **Повтор отвечает `200`, даже если новый такой запрос был бы отклонён** — стратегию сняли или превышен лимит активных заданий. Это осознанно: повтор возвращает уже созданный ресурс.
- **Хранение и обслуживание.** Отдельная таблица с уникальным индексом, запись в каждой транзакции создания, периодическая очистка.
- **Ожидание при гонке.** Второй из одновременных запросов ждёт фиксации первого: в PostgreSQL — на блокировке уникального индекса, в SQLite — из-за последовательной записи.

## Условия пересмотра

Решение пересматривается, если выполняется хотя бы одно из условий:

- создание задания перестаёт быть короткой транзакцией без внешних вызовов — например, снимок данных фиксируется синхронно при создании. Понадобятся состояние ключа «в обработке» и ответ `409` на одновременный повтор;
- клиенты повторяют запросы позже чем через 24 часа (офлайн-клиенты, внешние очереди) или таблица ключей заметно нагружает БД;
- доля ответов `409 idempotency_key_reused` на запросы с одинаковым смыслом превышает 1% — перейти на нормализованный отпечаток;
- API становится публичным или появляются сторонние интеграции — согласовать поведение с черновиком IETF и хранить первоначальный ответ;
- задания начинают ставиться через брокер сообщений (условия пересмотра ADR 0001) — повторную доставку придётся отсекать и на стороне worker.
