# /clarify — запрос от команды

Режим: !`echo "${HARNESS_MODE:-interactive}"`

Вход: `$ARGUMENTS`. `#N` — прочитай issue `change-request` (`gh issue view N --comments`); иначе — текст пользователя.
Автор запроса — тот, кто написал текст или issue; решение записывается от его имени.

## 1. Классифицируй
| Тип | Признак | Что делать |
|---|---|---|
| Вопрос | «как у нас…», «что будет, если…» | Ответь по спецификации со ссылками на файл и раздел. Ответа нет — это пробел: предложи `/interview <тема>` или открой `question` |
| Уточнение | Поведение не меняется, формулировка неоднозначна | Решение + правка текста спецификации |
| Изменение | Меняется поведение, контракт или критерии | Impact analysis (п. 2) → решение → спецификация → задачи |
| Новое требование | Новый сценарий или функционал | Описание по `interview/question-bank.md` → новый сценарий `С<N>` → impact analysis → задачи |
| Вне MVP | Противоречит границам из `concept.md` §4/§12 или правилам курса | Объясни, предложи минимальную версию или перенос; решение — класса H |

## 2. Impact analysis — до любого кода (это же нужно для практики 8)
| Артефакт | Что меняется | Объём | Риск |
|---|---|---|---|
| `docs/requirements.md` С… | | | |
| `docs/api/openapi.yaml` | операции, схемы, коды ошибок | | совместимость для клиентов |
| `docs/tool-contract.md`, `docs/architecture.md`, ADR | | | |
| Код и тесты | модули, какие тесты меняются, какие новые | | регрессия |
| Задачи и PR | открытые issues и PR, которые меняют критерии | | |
| Курс | влияние на чек-лист текущей практики и срок | | баллы |
Найди затронутое поиском по спецификации (`grep -rn`), по открытым issues и PR (`gh issue list`, `gh pr list`) и по коду.

## 3. Недостающее
- Интерактивный режим: спроси одним раундом `AskUserQuestion` (до 4 вопросов, рекомендуемый вариант первым).
- Автономный режим (запрос пришёл из issue через `inbox`): impact analysis и вопросы — комментарием в issue; на недостающее —
  предположение по `decision-protocol`. Класс H (меняет объём, ломает влитое, задевает чек-лист) — не реализуй:
  метка `needs-human` и комментарий «Подтвердите: `/approve` или `/answer <вариант>`».

## 4. Запись и исполнение
1. Решение — `docs/product/decisions/<номер issue>-<slug>.md` (`decision-protocol`). Запрос пришёл текстом — создай issue
   `change-request` с текстом пользователя, номер станет идентификатором.
2. Спецификация — субагент `spec-writer`; один PR `docs: <что уточнили или изменили>`, рецензент по ротации; в теле — impact analysis.
3. Задачи на код и тесты — issues по шаблону `spec-dd` с `Depends on` PR спецификации; метка текущей практики, если изменение
   нужно к её сроку, иначе без метки (backlog). Затронутые открытые задачи — комментарий с новыми критериями.
4. Issue запроса: комментарий «разобрано» со ссылками, метка `triaged`; закрывается, когда влиты спецификация и задачи.

## 5. Итог
Тип запроса, решение, ссылка на PR спецификации, созданные и изменённые задачи, что ждёт подтверждения людей.
