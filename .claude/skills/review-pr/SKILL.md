# Review: $ARGUMENTS

Review засчитывается курсом только содержательное (скилл `course-rules`): вопрос или замечание по существу — что сломается,
что непонятно, чего не хватает в тестах. «LGTM» и пустой Approve не считаются и команде не помогают.

## 1. Контекст
- Репозиторий: ссылка из аргумента; число без `--cross` — `team-gambit`; `--cross` без ссылки — цель из
  `python3 scripts/harness/zadania.py brief pN --json` (`review.target`, при отсутствии PR за неделю — `review.backup`).
- `gh pr view <N> -R <repo> --json title,body,author,headRefOid,files,reviews,comments,closingIssuesReferences`,
  `gh pr diff <N> -R <repo>`, связанные issues, комментарии к строкам `gh api repos/<repo>/pulls/<N>/comments`.
- Не повторяй уже сделанные замечания (свои и чужие); если ты уже ставил Request changes — это повторное review (п. 5).
- Свой репозиторий: спецификация, на которую ссылается задача (`spec-dd`), и чек-лист практики.
- Перекрёстное: их README, их `docs/` (требования, контракт), задание практики из Zadania — чек-лист у всех команд общий.

## 2. Запусти, а не только прочитай
Код — проверь на голове PR в отдельном дереве, не трогая рабочую копию:
```bash
git fetch origin pull/<N>/head:review/pr-<N> && git worktree add .harness/state/review-<N> review/pr-<N>   # свой репозиторий
gh repo clone <repo> .harness/state/cross/<repo-name> -- --depth 50 && gh -R <repo> pr checkout <N>         # перекрёстное
```
Свой — `scripts/harness/check.sh`; чужой — их команда тестов из README, не дольше 10 минут. Итог запуска — в тело review.

## 3. Найди проблемы
Делегируй субагенту `reviewer` (он не пишет в GitHub и не меняет файлы): передай репозиторий, номер PR, путь к дереву,
спецификацию и чек-лист. Он вернёт находки с файлом, строкой, серьёзностью и предложением. Каждую находку проверь сам —
открой строку в файле на голове PR; неподтверждённые выбрось. Что искать:
- расхождение со спецификацией или контрактом (поля, коды ошибок, переходы состояний);
- поведение на ошибках и границах: неверные параметры, неизвестная операция, повтор, отмена, падение Tool;
- злодейства и гонки (для Job — З1–З6 из Zadania `tasks/p3_job/README.md`);
- тесты: какой критерий или негативный случай не покрыт; тест, который проходит при неверном коде;
- архитектурные правила: ядро без фреймворка и БД, Dispatcher без условий по именам Tool.

## 4. Опубликуй
Каждый комментарий: **проблема → конкретный сценарий, где она проявится → предложение**. Привязка — к строке нового файла
(`side: RIGHT`, номер строки в файле на голове PR). Общее — в тело review: что проверено, итог запуска, обязательное и
необязательное.

Вердикт:
- свой репозиторий — `REQUEST_CHANGES`, если без правки нельзя вливать (противоречие спецификации или чек-листу, красные
  тесты, потеря данных); иначе `APPROVE` с комментариями, необязательное — в отдельный issue;
- перекрёстное — всегда `COMMENT` (approve там ни на что не влияет).

Публикуй одним запросом: JSON собери скриптом (`json.dump(..., ensure_ascii=False)`), тело начинается с `<!-- harness -->`:
```bash
gh api --method POST repos/<repo>/pulls/<N>/reviews --input <файл.json>
# {"commit_id": "<headRefOid>", "event": "...", "body": "...", "comments": [{"path": "...", "line": 12, "side": "RIGHT", "body": "..."}]}
```
Проверь, что комментарии встали на нужные строки: `gh api repos/<repo>/pulls/<N>/comments`.

## 5. Повторное review
После правок автора пройди по своим прежним замечаниям: исправлено — отметь ответом; спорное — ответь по существу.
Всё обязательное закрыто — `APPROVE` с итогом проверки.

## 6. Итог
Верни ссылку на review, вердикт, число замечаний (обязательных и необязательных) и итог запуска тестов.
