# /practice — очередная практика целиком

## Состояние на старте
- Режим: !`echo "${HARNESS_MODE:-interactive}"`
- Ты (ACTOR): !`gh api user --jq .login 2>&1`
- Активные практики: !`python3 scripts/harness/zadania.py current 2>&1`

Аргументы: `$ARGUMENTS`. Практика — `pN` из аргументов, иначе первая (самая срочная) из активных. `--phase` — выполнить одну фазу.

## Принципы
1. **Повторяемость.** Каждая фаза сначала смотрит на GitHub (`scripts/harness/status.py`) и пропускает сделанное. Запуск раз в несколько часов доводит практику до сдачи; два запуска подряд не создают дублей.
2. **От своего имени.** Только задачи ACTOR, его PR и review, где он рецензент. Общие фазы (разбор, план) делает тот, кто запустил первым; отчёт — назначенный участник.
3. **Сначала спецификация** — скилл `spec-dd`. **Неясное** — скилл `decision-protocol`. **Баллы и правила** — скилл `course-rules`.
4. **Автономный режим** — ни одного вопроса человеку; интерактивный — вопросы только классов M и H, пачкой, не больше одного раза за фазу.
5. **Время.** Меньше 24 часов до срока — порядок: влить готовое → review → отчёт → новое. Меньше 6 часов — новых задач не начинать.

## Фаза 0. Подготовка
```bash
python3 scripts/harness/zadania.py sync
python3 scripts/harness/zadania.py brief pN --json
gh label list -R AIProgramIngeneering2026/team-gambit --search practice: --json name --jq length   # 0 → scripts/harness/bootstrap.sh
```
Выполни скилл `inbox`: ответы команды на вопросы и запросы изменений могут поменять спецификацию до планирования.
Сними состояние: `python3 scripts/harness/status.py pN --json`.

## Фаза 1. Разбор задания (если трекинг-issue практики ещё нет)
Прочитай `tasks/pN.md`, все `linked_files` из брифа, шаблон отчёта, `tasks/review_pN.md`, строку практики в `tasks/project.md`.
Составь бриф: для каждого пункта чек-листа `C1…Cn` — что должно лежать в `main` к сроку и чем это проверить; личные
требования (свой PR или review, перекрёстное review); разделы отчёта, требующие отдельных данных (таблицы злодейств, карт и т. п.).

## Фаза 2. Спецификация
Для каждого `Ci` найди, какие разделы `docs/` его описывают (карта из `spec-dd`), и проверь готовность по Definition of Ready.
Пробел — задача типа `docs` в плане, она идёт первой. Неясность — протокол решений (вопрос, предположение или blocked).
Код по пункту чек-листа не планируй, пока его спецификация не готова или не запланирована раньше.

## Фаза 3. План (если трекинг-issue нет)
Непосредственно перед созданием ещё раз проверь, что трекинг-issue нет: другой участник мог запустить план одновременно.
- **Задачи.** Одна задача — один PR, проверяемые критерии, ссылки на спецификацию и пункты чек-листа (шаблон в `spec-dd`).
  Сначала ищи в открытых issues подходящую (backlog практики 1, например «Инфраструктура: каркас проекта и CI»):
  добавь ей метку `practice:pN` и критерии комментарием, а не создавай дубль.
- **Распределение.** У каждого участника — хотя бы одна задача-PR (личное участие), нагрузка примерно равная; зависимые
  задачи — так, чтобы первая не блокировала всех. Рецензент задачи — `reviewer` исполнителя из `.harness/config.toml`.
- **Перекрёстное review** (с p3): каждому участнику — свой PR проверяемой команды, когда они появятся.
- **Отчёт** сдаёт `members[(N - 1) % 3]`.
```bash
gh issue create -R AIProgramIngeneering2026/team-gambit --title "<задача>" --label practice:pN --assignee <login> --body-file <файл>
gh issue create -R AIProgramIngeneering2026/team-gambit --title "[pN] <название практики>: план и статус" \
  --label practice:pN --label harness:tracking --body-file <файл>
```
Тело трекинг-issue: срок; таблица «пункт чек-листа → задачи → исполнитель → рецензент»; перекрёстное review; кто сдаёт отчёт;
как запускать харнес; в конце — блок `<!-- harness:plan {"practice": "pN", "items": [{"issue": 21, "checklist": ["C1"], "assignee": "...", "reviewer": "...", "depends_on": []}]} -->`.

## Фаза 4. Реализация своих задач
Свои открытые задачи `practice:pN` без влитого PR — в порядке зависимостей (зависимость не влита — пропусти, отметь).
Каждую делегируй субагенту `implementer` с заданием «выполни скилл implement-issue для #<N>»; независимые — параллельно,
не больше двух, каждая в своём worktree. Проверь их итог: ссылка на PR, зелёный check.sh.
Перехват: если до срока меньше `harness.takeover_hours_left` часов, а у задачи участника нет PR — комментарий
«Перехватываю задачу по правилу 48 часов» в issue и реализация (скилл `implement-issue` это проверяет).

## Фаза 5. Review
- В командном репозитории — PR, где ACTOR запрошен рецензентом или является `reviewer` автора, а его review нет на последнем
  коммите → скилл `review-pr <N>`.
- Перекрёстное (с p3): если в `status.py` у ACTOR нет `cross_reviews` — PR проверяемой команды за эту неделю, который ещё не
  смотрел никто из нас (код важнее документов) → `review-pr <ссылка> --cross`. PR нет — запасная команда, запиши это в трекинг-issue.

## Фаза 6. Ответ на замечания
Свои открытые PR с `CHANGES_REQUESTED` или новыми комментариями после последнего push → `implement-issue <N>`, пункт 6.

## Фаза 7. Вливание
Свой PR вливай, когда есть содержательное одобрение участника команды, проверки зелёные (`gh pr checks <N>`) и нет конфликтов:
```bash
gh pr merge <N> --squash --delete-branch
```
Рецензент молчит больше 24 часов, а до срока меньше `harness.report_fallback_hours` часов — по правилам курса можно влить без review:
напиши это в PR и в трекинг-issue, это пойдёт в «Препятствия». Потом убери рабочее дерево задачи: `git worktree remove .claude/worktrees/issue-<N>`.

## Фаза 8. Аудит чек-листа
Делегируй субагенту `verifier`: проверить `origin/main` по каждому `Ci` с доказательствами (файл, тест, вывод команды).
Опубликуй таблицу комментарием в трекинг-issue (первая строка `<!-- harness:audit -->`; есть прежний — обнови его
`gh api --method PATCH repos/<repo>/issues/comments/<id>`). Пробелы при запасе времени — новые задачи (фаза 3, без нового трекинга).

## Фаза 9. Отчёт
Когда аудит зелёный или до срока меньше `harness.report_fallback_hours` часов — скилл `practice-report pN`
(он сам проверит, твоя ли очередь сдавать).

## Фаза 10. Итог
Выведи и добавь комментарием в трекинг-issue (кратко, с маркером `<!-- harness -->`):
- что сделано от имени ACTOR — ссылки на PR, review, issues;
- что ждёт людей: вопросы `question`, задачи `blocked`/`needs-human`, PR без review;
- пункты чек-листа: готово / в работе / под угрозой;
- сколько осталось до срока и что сделает следующий запуск.
