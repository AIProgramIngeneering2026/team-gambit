# Правила курса — выжимка для агента

Источник истины — клон Zadania (`python3 scripts/harness/zadania.py brief pN` печатает путь): `ПРАВИЛА.md`, `README.md`,
`tasks/pN.md`, `templates/pN.md`, `tasks/review_pN.md`, `tasks/project.md`. Перед решением, от которого зависят баллы,
перечитай нужный файл: правила меняются от практики к практике, выжимка ниже может устареть.

## Ритм
- Практика по субботам; задание `tasks/pN.md` выкладывается в день пары. Срок — воскресенье следующей недели, 23:59 по Екатеринбургу (+05:00).
- Проверяется состояние `main` командного репозитория на момент срока. Опоздание отчёта — не больше 50% баллов.
- Командный балл — по чек-листу из `tasks/pN.md`: выполнено всё — полный, больше половины — половина, меньше — ноль.

## Личное участие (каждый участник, каждая практика)
- Свой **влитый** PR в командном репозитории или **содержательное** review в рамках практики. Засчитывается только по ссылкам в разделе «Вклад участников» отчёта. Нет ссылок — 0.
- Один PR засчитывается только в одной практике.
- Исключение — p2: участие считалось по паре (мини-тест + `[poker]`).
- С p3 — перекрёстное review: каждый участник делает содержательное review хотя бы одного PR проверяемой команды (`tasks/review_pN.md`; права не нужны, review комментариями, лучше к строкам). Нет PR у проверяемой — запасная команда, отметить в «Препятствиях».
- Содержательное review: вопрос или замечание по существу — что сломается, что непонятно, чего не хватает в тестах. «Ок», «LGTM», пустой Approve не засчитываются.

## Командный процесс (ПРАВИЛА + CONTRIBUTING.md)
- В `main` только через PR; прямой push и force-push запрещены. Squash and merge, вливает автор после review.
- Открыл PR — назначь рецензента из команды (ротация — `reviewer` в `.harness/config.toml`). Рецензент отвечает в течение 24 часов.
- Задачи — issues с исполнителем. Если за 48 часов до срока по задаче нет PR, любой участник может её перехватить, написав об этом в issue; задача засчитывается сделавшему.
- Участник без личного участия две практики подряд может быть исключён — следи, чтобы у каждого был вклад.

## Отчёт в Zadania
- Файл `teams/gambit/pN.md` строго по `templates/pN.md`: все разделы «## …» шаблона есть и не пустые; HTML-комментарии содержимым не считаются.
- Один PR от любого участника **из своего fork** (прав на запись в Zadania нет). Название — `pN — gambit`. Менять можно только `teams/gambit/`.
- Бот проверяет структуру (`tools/check_pr.py`); красная проверка = работа не принята. Метку `full`/`half`/`rework` ставит преподаватель, вливание автоматическое.
- В «Вкладе участников» — полные ссылки `https://github.com/AIProgramIngeneering2026/team-gambit/pull/N` на PR и review каждого, включая перекрёстное review.

## Контрольные точки проекта (tasks/project.md)
| Практика | К сроку в main |
|---|---|
| 3. Доменное ядро | Job с проверкой переходов; Dispatcher и Registry; ≥2 Tool; ошибки «неизвестная операция» и «неверные параметры»; ядро без фреймворка и БД; первые тесты (обычный путь, злодейства З1–З6, две ошибки), запуск одной командой |
| 4. API и хранение | API соответствует контракту; хранилище с миграциями (SQLite); единый формат ошибок; идемпотентное создание Job |
| 5. Тесты и review | У каждого свой PR с тестами и своё review; позитивные, негативные, параметризованные тесты; CI зелёный |
| 6. Внешняя зависимость | Адаптер с timeout и retry; недоступность и мусорный ответ; fake-сервис; интеграционные или контрактные тесты |
| 7. Диагностика и запуск | Логи с correlation ID; health check с проверкой СУБД; конфигурация из окружения; СУБД отдельным сервисом, миграции при запуске; запуск из чистого клона одной командой |
| 8. Изменение и защита | Новое требование по жребию; impact analysis до кода; изменение через обычный PR-процесс; регрессия зелёная; демо основного и отказного сценария |

## Что харнес не делает
- Лекционные ДЗ (`hw1`–`hw3`) и отработки — индивидуальные работы, их делает сам студент.
- Мини-тесты и работа на паре (`[poker]`, `[job]`) — только во время пары, лично.
