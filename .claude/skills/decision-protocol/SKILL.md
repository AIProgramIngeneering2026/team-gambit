# Протокол решений

Режим: `HARNESS_MODE=autonomous` — человека нет (запуск через `scripts/harness/run.sh`); иначе — интерактивный.

## 1. Сначала ищи ответ
По порядку: `docs/product/decisions/` → `docs/requirements.md` → `docs/concept.md` → контракты (`docs/api/openapi.yaml`,
`docs/tool-contract.md`) → `docs/architecture.md` и `docs/adr/` → открытые и закрытые issues с меткой `question` → правила курса.
Нашёл — сошлись на источник (файл и раздел) в коде, PR или комментарии. Противоречие между документами — это тоже вопрос (п. 2).

## 2. Не нашёл — определи класс
| Класс | Признаки | Пример в TradeLab |
|---|---|---|
| **L — техническое** | Не видно пользователю и другим командам, легко поменять | имя модуля, структура тестов, формат лога |
| **M — продуктовое обратимое** | Меняет поведение или контракт, но до релиза меняется одним PR | окно сигнала по умолчанию, код ошибки, лимит длины периода |
| **H — необратимое или меняет объём** | Удаление данных, смена темы или стека, отказ от пункта чек-листа, новая внешняя зависимость, решение за преподавателя, противоречие с правилами курса | убрать отмену Job, сменить поставщика данных, перенести срок |

## 3. Действуй по классу
| Класс | Интерактивный режим | Автономный режим |
|---|---|---|
| L | Решай сам, одна строка в описании PR «Решения по ходу» | То же |
| M | Спроси сразу (AskUserQuestion, до 4 вопросов за раз, рекомендуемый вариант первым), ответ запиши решением | Выбери консервативный вариант (меньше обещаний в контракте, строже проверка, проще откатить), запиши **предположение**, открой issue-вопрос, продолжай |
| H | Спроси и не продолжай эту часть до ответа | Не решай. Задача — метка `blocked`, issue-вопрос с меткой `needs-human`; переходи к независимой работе; в итоге и в «Препятствиях» отчёта — что ждёт ответа |

Не выдумывай требования молча: каждое решение класса M и H видно в `docs/product/decisions/` и в issue.
В автономном запуске не больше 5 новых вопросов: остальное сгруппируй в один issue «Вопросы по <теме>».

## 4. Запись решения
Решение = issue с меткой `question` + файл `docs/product/decisions/<номер issue>-<slug>.md`. Номер issue — идентификатор решения (`D-23`), он уникален и не конфликтует между параллельными PR.

```markdown
# D-23. Окно сигнала по умолчанию
- **Статус:** предположение | принято | заменено D-31 | отклонено
- **Источник:** issue #23; интервью с @login 2026-11-20 | предположение агента в PR #25
- **Вопрос:** …
- **Решение:** …
- **Варианты:** A — … (выбран), B — …
- **Влияние:** docs/tool-contract.md §6, docs/api/openapi.yaml `SignalRequest`, issues #24, #26
```
Статус «предположение» → после ответа человека «принято» (ответ совпал) или «заменено» (новый файл решения + правка спецификации + перепланирование задач, см. скилл clarify).

## 5. Issue-вопрос команде
Заголовок `[вопрос] <коротко>`, метки `question`, `practice:pN`, при необходимости `assumption` или `needs-human`. Тело:

```markdown
<!-- harness -->
**Контекст:** где возник вопрос (задача #N, файл и раздел спецификации).
**Вопрос:** один вопрос, на который можно ответить одной строкой.
**Варианты:**
- **A (рекомендую)** — … Последствия: …
- **B** — … Последствия: …
**Что сделано сейчас:** принят вариант A как предположение D-<номер> / задача #N заблокирована.
**Как ответить:** комментарий `/answer A` или `/answer <свой вариант>` — либо `/interview` в Claude Code.
```
