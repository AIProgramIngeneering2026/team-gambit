# /interview — агент спрашивает, команда решает

Режим: !`echo "${HARNESS_MODE:-interactive}"`

Интервью требует человека. В режиме `autonomous` не начинай: выведи список открытых вопросов
(`gh issue list --label question --state open`) и подскажи запустить `/interview` в интерактивной сессии.

## 1. Повестка (`$ARGUMENTS`)
| Аргумент | Повестка |
|---|---|
| пусто или `pending` | Открытые issues `question` (сначала `needs-human` и блокирующие задачи) и решения со статусом «предположение» в `docs/product/decisions/` |
| `<тема>` (например «сигнал», «сравнение», «ошибки поставщика») | Пробелы спецификации по теме: что не определено, противоречит или не проверяемо — пройди карту из `spec-dd` |
| `feature <функционал>` | Описание нового или неясного функционала по шаблону из [question-bank.md](question-bank.md) |
| `next` | Что понадобится в ближайших практиках (`course-rules`, таблица контрольных точек) и чего для этого нет в спецификации |

Сначала выполни скилл `inbox`: часть вопросов могла получить ответ в GitHub.
Составь повестку и покажи её одним сообщением: вопросов, тем, ориентировочно раундов.

## 2. Раунды вопросов
- `AskUserQuestion`: до 4 вопросов за раз, у каждого 2–4 варианта, рекомендуемый — первым с пометкой «(рекомендую)»,
  в описании варианта — последствия для контракта, сроков и тестов. Свой вариант пользователь даст через «Other».
- Задавай только то, чего нет в спецификации и решениях; не переспрашивай решённое.
- Ответ породил новые неясности — следующий раунд. Пользователь просит остановиться — останавливайся; оставшееся
  остаётся открытыми вопросами.
- Описание функционала (`feature`) — вопросы по шаблону, пока не будет: цель и участник, основной поток, правила,
  ошибки, критерии приёмки «Дано/Когда/Тогда», что вне объёма.

## 3. Подтверждение
Покажи сводку: решение по каждому вопросу и какие документы изменятся. Один вопрос: «Публикуем?» —
«Да» / «Поправить» (что поправить — через Other). После «Поправить» — правка и снова сводка.

## 4. Запись
1. Для каждого решения — файл `docs/product/decisions/<номер issue>-<slug>.md` по формату `decision-protocol`.
   Вопроса без issue — создай issue `question` (это идентификатор и уведомление команде), потом закроешь его.
2. Правку спецификации делегируй субагенту `spec-writer`: передай решения, затронутые документы и требование согласованности
   между `requirements.md`, `openapi.yaml`, `tool-contract.md`, `architecture.md`, ADR.
3. Одна ветка и один PR от ACTOR: `docs: уточнение требований — <тема>`, рецензент по ротации, метка текущей практики.
   В теле — таблица «вопрос → решение → где изменено» и ссылки на issues. Перед PR — `scripts/harness/check.sh`.
4. Каждый закрытый вопрос: комментарий с решением и ссылкой на PR, метка `answered`, закрыть issue.
5. Перепланирование: решение меняет критерии открытых задач или влитый код — комментарий в задаче с новыми критериями
   (или новая задача), заметка в трекинг-issue практики. Предположение подтвердилось — статус «принято», код не трогаем.

## 5. Итог
Сколько вопросов закрыто и какими решениями, ссылка на PR спецификации, что осталось открытым, какие задачи перепланированы.
