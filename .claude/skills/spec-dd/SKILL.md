# Spec-driven разработка в TradeLab

## Карта спецификаций — источник истины
| Что | Где | Идентификаторы |
|---|---|---|
| Замысел, границы MVP | `docs/concept.md` | разделы 1–16 |
| Сценарии и критерии приёмки | `docs/requirements.md` | `С1`–`С6`, критерий — `С1.2` (второй пункт «Дано/Когда/Тогда» сценария С1) |
| Компоненты, жизненный цикл Job | `docs/architecture.md` | разделы `§2`, `§3.1` … |
| Архитектурные решения | `docs/adr/NNNN-*.md` | `ADR 0001` |
| HTTP API | `docs/api/openapi.yaml` | `operationId`, схемы `components/schemas/*`, коды ошибок `ErrorCode` |
| Контракт стратегий | `docs/tool-contract.md` | разделы `§1`–`§7` |
| Продуктовые решения | `docs/product/decisions/` | `D-<номер issue>` |
| Задание практики | Zadania `tasks/pN.md` | пункты чек-листа `C1`… (`zadania.py brief pN`) |

## Порядок работы
1. **Спецификация раньше кода.** Поведение, которого нет в спецификации, в код не попадает. Нужна новая или изменённая спецификация — отдельная задача и отдельный PR `docs: …`, он вливается первым (или идёт первым коммитом того же PR, если правка мелкая и не спорная).
2. **Задача ссылается на спецификацию.** В issue — разделы спецификации и пункты чек-листа, которые она закрывает, и проверяемые критерии готовности.
3. **Тесты из критериев.** Каждый критерий задачи — хотя бы один тест; имя или docstring теста ссылается на критерий: `test_c1_2_repeat_with_same_key_returns_same_job`, «З3» для злодейств практики 3. Сначала тест (красный), потом код (зелёный).
4. **Код соответствует спецификации, а не наоборот.** Нашёл расхождение — либо код неправ (исправь), либо спецификация неполна (протокол решений), но не меняй спецификацию молча под код.
5. **Проверка соответствия.** `scripts/harness/check.sh`: тесты, OpenAPI, ссылки в документах, независимость ядра. Для практики — аудит чек-листа агентом verifier.

## Готовность задачи (Definition of Ready)
- [ ] критерии проверяемы (можно написать тест или указать файл и раздел);
- [ ] входы, выходы и ошибки определены в контракте;
- [ ] открытые вопросы закрыты решением или предположением (`decision-protocol`);
- [ ] зависимости (`Depends on #N`) влиты или не блокируют.
Не готова — сначала довести спецификацию, не начинать код.

## Шаблон issue задачи
```markdown
<!-- harness -->
**Зачем:** пункт чек-листа C3 практики p3 (Dispatcher не знает конкретных Tool).
**Спецификация:** docs/architecture.md §2 (Dispatcher), docs/tool-contract.md §1, §7.
**Критерии готовности:**
- [ ] C3.1 Dispatcher получает Tool из Registry по имени; в коде нет условий по именам стратегий.
- [ ] C3.2 Исключение Tool переводит Job в failed с кодом tool_failed (architecture §3.1).
**Тесты:** обычный путь; падение Tool; неизвестная операция.
**Зависит от:** #21 (Job), #22 (Registry).
**Рецензент:** @<по ротации из .harness/config.toml>
```

## Шаблон PR
Название — по CONTRIBUTING: `<тип>: <что изменилось>` на русском (`feat: Dispatcher переводит падение Tool в failed`).
```markdown
<!-- harness -->
## Что сделано
- …
## Соответствие спецификации
| Критерий | Где реализовано | Тест |
|---|---|---|
| C3.1 | src/tradelab/domain/dispatcher.py | tests/domain/test_dispatcher.py::test_c3_1_… |
## Решения по ходу
- L: … / D-23 (предположение, issue #23)
## Как проверить
`scripts/harness/check.sh` — итог: …
Closes #N
```

## Правка спецификации
- Меняй минимально и согласованно: одно решение — во всех затронутых документах сразу (requirements ↔ openapi ↔ tool-contract ↔ architecture).
- Новый сценарий — следующий номер `С7`, с целью, участником, потоком и критериями «Дано/Когда/Тогда».
- Архитектурное решение с альтернативами — новый ADR по образцу `docs/adr/0001-*.md`: дата, статус, контекст, решение, альтернативы, цена, условия пересмотра.
- После правки: `scripts/harness/check.sh` (OpenAPI и ссылки).
