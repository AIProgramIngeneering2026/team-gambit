# Реализация задачи #$ARGUMENTS

Перед работой прочитай скиллы `spec-dd` и `decision-protocol`. Всё ниже — от имени `gh api user --jq .login` (дальше ACTOR).

## 1. Проверь, что задача твоя и готова
- `gh issue view $0 --json number,title,body,assignees,labels,state,comments`.
- Исполнитель — ACTOR. Если нет: работай, только если до срока меньше `harness.takeover_hours_left` часов, PR по задаче нет и в issue ты оставил комментарий «Перехватываю задачу по правилу 48 часов» (правило курса). Иначе остановись и сообщи.
- Уже есть PR (`gh pr list --search "$0 in:body" --state open`)? Продолжай в его ветке: исправляй замечания review (п. 6), новый PR не открывай.
- Проверь готовность по Definition of Ready из `spec-dd`. Не готова — протокол решений; в автономном режиме при классе H поставь `blocked` и закончи.

## 2. Ветка и рабочее дерево
Тип ветки — по сути задачи: `feat`, `fix`, `test`, `docs`, `chore`. Имя — `<тип>/$0-<коротко-латиницей>`.
```bash
git fetch origin
git worktree add .claude/worktrees/issue-$0 -b <тип>/$0-<slug> origin/main   # или существующая ветка PR
cd .claude/worktrees/issue-$0
```
Работай только в этом дереве: так параллельные задачи и рабочая копия человека не мешают друг другу.

## 3. Каркас проекта (если кода ещё нет)
Нет `pyproject.toml`, а задача требует кода — создай каркас по стеку из заявки (Python 3.11+, uv, pytest):
`pyproject.toml` (uv, pytest, ruff), `src/tradelab/domain/` (ядро без фреймворка и БД), `tests/`, команда тестов в `README.md`
(`uv run pytest`). Каркас — первым коммитом и только если его не делает другая открытая задача (инфраструктурная задача в backlog).

## 4. Тесты, затем код
1. Для каждого критерия задачи — тест, имя ссылается на критерий (`test_c3_2_tool_exception_fails_job`). Злодейства практики 3 — `test_z3_…`. Негативные случаи обязательны: неверные параметры с полем, неизвестная операция, запрещённые переходы.
2. Запусти — новые тесты должны быть красными по правильной причине.
3. Минимальный код, который делает их зелёными и соответствует спецификации. Архитектурные правила: ядро (`src/tradelab/domain`) не импортирует FastAPI, SQLAlchemy, httpx и драйверы БД; Dispatcher не знает конкретных Tool; переходы Job проверяет сам Job.
4. Нашёл расхождение кода и спецификации — не подгоняй спецификацию под код: протокол решений.

## 5. Проверки и коммиты
- `scripts/harness/check.sh` — должен быть зелёным. Красный — исправляй; не отключай и не ослабляй тесты.
- Самопроверка: пройди diff против таблицы «критерий → код → тест»; лишнего (не из задачи) в PR нет.
- Коммиты по CONTRIBUTING: `<тип>: <что изменилось>` на русском, одно логическое изменение на коммит.

## 6. PR
```bash
git push -u origin HEAD
```
Тело PR — по шаблону из `spec-dd` (первая строка `<!-- harness -->`, таблица соответствия, решения по ходу, итог check.sh, `Closes #$0`).
Тело собирай во временном файле, затем:
```bash
gh pr create --title "<тип>: <что изменилось>" --body-file <файл> --label practice:pN --assignee @me \
  --reviewer <reviewer участника ACTOR из .harness/config.toml>
```
Если PR уже был и пришли замечания: ответь на каждое — исправлением (коммит, ответ «исправлено в <sha>») или аргументом со ссылкой на спецификацию; затем `gh pr edit <N> --add-reviewer <рецензент>` для повторного review. После `harness.max_fix_rounds` раундов без одобрения — метка `needs-human` и комментарий, что осталось спорным.

## 7. Итог
Верни: ссылку на PR, итог check.sh (команда и последние строки), принятые решения (L и D-номера), открытые вопросы.
